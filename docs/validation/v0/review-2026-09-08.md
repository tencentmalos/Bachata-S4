## 3. 需要修复的问题（按影响排序）

### R1 [P1] guest 正确性和停止分类仍失败，不能判定执行核心已可用

位置：`src/core/guest_cpu/fex/fex_context.cpp:472–491`、`BuildRunResult`，对应 C01/C02/D05。

重跑中栈 push/pop 没有预期结果，SSE2 输出错误；单独 fixture 中的 HLT 也被报告为 `Returned`。这意味着即使到达 return gate、读到 SafePoint，也不能说明 fixture 的全部指令按预期执行。当前 12 个失败包含测试本身的缺陷（R2），但 R2 不能解释其他栈/SSE2/HLT 失败。

建议先修测试 oracle，再缩成每个进程一条 fixture，记录 guest bytes、初始/最终状态、内存副作用、translation identity。根因尚未证明，不能把“只剩 spill/frame 指针问题”当作已排他确认的结论。

### R2 [P1] 整数 fixture 编码错误，正确执行也无法通过 G01

位置：`tests/guest_cpu/guest_execution_tests.cpp:183–188`。

`49 01 C8` 实际是 `add r8, rcx`，测试种子与断言却按 `add r8, r9`（应为 `4D 01 C8`）设计。此时 rcx 为零，得到 r8=0x1000 本身不能证明 FEX 没有执行 ADD。独立 LLVM 反汇编已验证。

应使用可重建汇编源码生成 fixture，并独立校验字节/反汇编；先更正该用例和基于它的诊断记录，再定位余下失败。G03d 也仅以两个内存槽的 OR 判定写入，应改为逐槽检查，避免部分写入伪装完整成功。

### R3 [P1] Protect 修改子范围，却把整个 mapping 登记成新权限

位置：`src/core/guest_cpu/api/address_space.cpp:413–432`。

复现：先 Map 两个 host pages 为 R，仅把第一页 Protect 为 RW。系统第二页仍是 R，但 `found->permission = permission` 修改了整个 mapping，`ValidateRange(第二页, Write)` 返回成功。随后显式 Write/返回的 writable span 可能直接触发 host fault；反向收紧则会错误拒绝未修改页。

这是 4 KiB 下同样成立的多页 mapping 问题。应拆分 mapping 区间、分别维护 generation/permission，或在尚未支持拆分时拒绝非整 mapping 请求，并保证失败不改变任何状态。

### R4 [P1] pin 与 Protect 没有互锁，验证和获取 pin 也非原子

位置：`address_space.cpp:393–433`、`523–534`、`497–519`。

Swan 复现：获得 writable pin 后，Protect(R) 仍成功。借出的可写 span 立即失去原权限，违反 M13；文档和 LoadCode 注释声称 Protect 会拒绝，实际没有检查 pins。

另外 `AcquirePinnedSpan` 先通过 `ValidateRange` 的锁，再单独加锁登记 pin，中间可被 Unmap/Protect 插入；Read/Write 同样在校验后释放锁再 memcpy。应把检查、lease 登记与映射生命周期做成原子协议，Protect/Unmap 一致地等待或返回 Busy，显式访问也持有有效 lease。

### R5 [P1] QuiescenceToken 不证明 CPU/writers 静止，缓存失效仍可与 Run 竞争

位置：`address_space.cpp:542–562`、`523–534`；`fex_context.cpp:472–491,564–590`。

Quiesce 只检查瞬时 pins，返回 stopped_threads=0；之后新 writable pin 仍可取得，已在 Swan 复现。它没有关联 CPU context，也不阻止新 Run/线程进入。backend InvalidateCode 只检查 token 非零和当下 running；Run 在解锁后才设置普通 bool `running`，并没有与清 cache 的整段形成互斥。

因此存在“Run 已通过 owner 检查 → controller 看见未 running 并清缓存 → owner 进入 JIT”的交错；ReadRegisters 与 running/实际寄存器更新也没有共同同步。只把 bool 改 atomic 仍不能关闭整个事务窗口。

需要 context 统一 quiesce 门闩、owner 发布的停止回执和新执行/writer 准入控制，token 绑定具体 context/address space/epoch；失效成功之前完成实际 cache 同步。当前 token 不能作为跨线程改代码的安全凭据。

### R6 [P1] 验收 runner 硬编码 PASS，并漏掉已执行的 guest 失败

位置：`scripts/android/run-v0-tests:377–399`、suite 注册与 `SUITE_MAP`。

空构建目录仍输出 B02/B05/B06 三项 PASS；本次没有运行对应检查，也未读取绑定当前 artifact hash 的检查结果。runner 只包含 host suites 与 bionic init smoke，不调用 guest_execution_tests，于是已知执行失败继续留在 NOT_RUN，并把 backend 描述为不存在。

部分 PASS 的映射也超出实际验证范围：M05 只是 C++ API 拒绝，不是 guest fault；M07 仅 generation 更新；M10 仅 alias 注册；D03 是手工 snapshot 类型检查，不是实际 fault 归属；H01 手工 frame 没验证 guest callee-saved/red zone。scope_note 可以解释辅助证据，但不能将完整验收项升为 PASS。

应把 unit evidence 和端到端验收分开；无当前运行证据即 NOT_RUN，真实失败即 FAIL；同时记录进程退出码/timeout。构建锁、FEX 下游 SHA 和 capabilities 应读取实际产物，不硬编码旧版本。当前 21/60 不能当成完成比例。

### R7 [P1] typed HLE 的指针验证没有覆盖 buffer 长度和持有期

位置：`src/core/guest_cpu/hle/call_adapter.h:167–190`。

`char*`/`void*` 只检查一个字节，`T*` 只检查一个 T，随即返回裸 host 指针且不持 pin。对于 `(char* buffer, size_t length)`，页末指针加跨页长度可以通过 adapter，callee 实际使用时越界；并发 Unmap 也可在验证后发生。现有单值指针测试不足以证明 H04/M13。

需要显式 guest span/长度关系元数据、调用期 lease，并对未声明的 buffer 语义拒绝或要求 callee 经过统一访问器。另有 HLE 异常未捕获、pointer return 未验证等后续接 gate 前必须补齐的边界。

### R8 [P2] 64 GiB “FEX 硬地址上限”的依据不成立

位置：`fex_context.cpp:163–171`、`BackendCapabilities::max_guest_address` 及 `docs/fex-guest-execution-bringup.md` §4.2。

所引 LookupCache 的确掩码计算索引，但随后比较完整 `GuestCode == Address`，不匹配转 L3；dispatcher 同样在 L2 读取后比较完整 RIP，不匹配则编译（FEX `LookupCache.h:196–219`、`Dispatcher.cpp:181–218`）。不能仅依据索引掩码推断高地址必然执行错误 block。

V0 可以保守限制地址区间作为实验策略，但应标注策略而非 FEX 能力上限。要认定高地址缺陷，需同一正确 fixture 在低/高 VA 的对照和命中错误 translation 的证据。现有记录称降低地址后同样失败，不能据此证明该根因已修复。

### R9 [P2] 构建入口与锁文件尚未形成可重复的 production library

位置：`cmake/fex/CMakeLists.txt:49` 起、`scripts/android/build-fexcore-android:25–70,87–128`。

文档推荐的 `V0_ENABLE_FEX=ON` 仍直接 FATAL_ERROR，新的 adapter 只由 shell 手工编译源码并串接静态库，没有 guest_cpu_fex 目标。脚本默认挑最新安装且有 atomic_ref 的 NDK，锁文件却仍是 r28c/f2；实际工作树为 r29/385a0cc4d。

应把 adapter 与必要私有编译定义组织成可复用 CMake target，供测试和将来 JNI 共同链接；锁定可重建的实际 FEX/NDK 配置。这里只确认当前机器增量构建通过，不宣称 clean-room 可重建。

## 4. 尚未实现的关键能力

以下是范围内缺项，不与已有代码 bug 混为一谈，也不能归因于缺少 16 KiB 设备：

- RequestInterrupt/WaitStopped/owner command queue、无 HLE loop 的 Pause/Stop、epoch 消费协议。
- 真实 typed HLE gate、guest callback 嵌套、FS/GS 多线程往返；当前 syscall handler 只设置一个 context 共享标志，没有实际停机或每线程 fault 分发。
- 有限一指令 Step、不可恢复 fault 状态机、稳定 DebugRegistry/native stop hook、与 ART 的 signal owner 协调。
- 真正的 alias backing、observer 权限聚合与 code publication 事务；现在的 alias 是元数据登记。
- JNI/普通 app、native Vulkan Surface 生命周期、输入闭环、Foundation DebugBus 与 reflection/packing 集成、长期资源回收检查。

Context 析构会直接清理仍登记的 native threads，没有 owner/运行态 shutdown 协议；全局 allocator/config 的清理也未按已设置标记配对。这应在 100 次生命周期测试前补齐，不能从一次 smoke 推断生产 context 可反复安全重建。

## 5. 建议下一轮顺序

1. **先恢复证据可信度**：修 fixture 编码、接入真实 guest suite、撤销无证据/部分覆盖的 PASS；新报告采用 Swan-4K scope，16 KiB 专属项延期且不计 PASS。
2. **单线程执行正确性**：整数/分支/内存/SSE2/HLT 分别独立验证；失败保留 bytes、独立预期、内存结果和正确版本身份。暂不把复杂 app 引入排错链。
3. **修 VM 与执行准入协议**：R3–R5 和 HLE spans；随后补并发失效、跨页原子、无 HLE loop 中断以及停止态读写。
4. **贯通 production target + app**：同一 guest_cpu_fex target 接 JNI；在普通 ART 进程验证初始化、真实 fixture、Stop/重启，然后接 HLE/callback 和最小 Vulkan。
5. **补 DebugBus/Step/LLDB 与生命周期验收**；满足当前 4 KiB 范围的 MUST 后再评价 V0 完成，16 KiB 独立恢复为后续里程碑。

本次源码审计不等于完整安全/性能审计。最有价值的进展是 bionic FEXCore 初始化已经可行；接下来关键是可验证的 guest 正确性和安全的执行/内存边界。
