# A0 首个验证 APK — 编译接线通过、真机启动/身份通过、guest 运行暴露 FEX 分配器平台缺陷

日期：2026-09-11。分支 `codex/android-fex-round2`。设备：AYN Thor（kalama / SD8Gen2），Android 13 / API 33 /
ARM64 / host page 4096，`ro.build.fingerprint = qti/kalama/kalama:13/TKQ1.231222.001/eng.Thor.20260206.163241`。

本记录对应 [N4-to-APK 执行 spec](../../specs/android-fex-round2-n4-to-apk.md) 的 **A0-a（工程/依赖/工具链锁）**
与 **A0-b（最小进程内闭环）** 的首次真机执行。结论:**APK 可重建、可安装、可启动;native 身份读取正确;
最初 in-process guest 执行在 `CreateFexContext` 内因 FEX 64-bit 对象分配器与 ART 启动期抢占 VA 而 `ERROR_AND_DIE`(SIGILL),
经适配器侧"等待地址空间静默"修复后,delay=0 冷启动 45/45 全通过,A0-b 进程内闭环成立(每次 10/10)。**

**A0-a 期间修复的编译接线缺陷（本次改动）：**

1. `build.gradle.kts` 缺少 Kotlin Android 插件 → `.kt` 源不编译进 dex，安装后 `ClassNotFoundException: MainActivity`
   启动即崩。已在根/`app` 两处加 `org.jetbrains.kotlin.android` 2.0.20 并设 `kotlinOptions.jvmTarget="17"`。
2. `app/build.gradle.kts` 用内联 `java.util.Properties()` —— Gradle Kotlin DSL 里裸 `java` 解析成 Java 插件扩展
   访问器而非 `java` 包，编译失败。改为顶部 `import java.util.Properties` 后不带限定使用。
3. `local.properties` 的 `ndk.dir` 与 `android.ndkVersion` 默认值冲突（CXX1104）。移除 `ndk.dir`，由 `ndkVersion` 决定。
4. CMake 版本 pin 3.30.5 不存在于 SDK（CXX1300）。改为 SDK 自带 3.22.1。
5. `validation_jni.cpp:232` 用 `std::string + ToString(StopReason)`，而 `ToString` 返回 `std::string_view`，
   NDK29 libc++ 无该 operator。用 `std::string{...}` 包裹视图。

依赖获取：除 `com.squareup:javapoet:1.10.0`（AGP 8.13.2 依赖）外全部命中本地 Gradle 缓存；该 jar 经隔离代理从
Maven Central 拉取（jar sha1 `712c178d35185d8261295913c9f2a7d6867a6007`，规范值），其余离线。

## 3. 真机执行结果（A0-b）

安装 `adb install -r`→`Success`；启动 `am start -n com.shadps4.fexvalidation/.MainActivity`。

- **通过**：Activity 正常 `performLaunchActivity`→`performResumeActivity`→`Displayed …MainActivity`。无
  ClassNotFound、无 dlopen/链接错误。
- **通过（native 身份，app 自报）**：`page_size=4096 pid=<pid> uid=10156`、`lib_build_id=<so BuildId>`、
  `native page_size(syscall)=4096`、`device API=33 model=AYN Thor targetSdk=35`、`va_bits=39`。
- **最初 FAIL（未修复时）**：worker 线程调用 `runGuestIncrement` → `CreateFexContext` 内 SIGILL,进程在首次

## 4. 根因（已定位:ART 启动期 VA 抢占的时序竞争，非 VA 布局不足）

`SetupHooks` → `Create64BitAllocator` → `OSAllocator_64Bit::AllocateMemoryRegions` 在 `[LOWER_BOUND=4GiB,
UPPER_BOUND=1<<VABits)` 区间用 `CollectMemoryGaps(/proc/self/maps)` + `StealMemoryRegion` 收集**相邻映射之间的空洞**,
需找到 **≥64 MiB** 的一段承载侵入式对象分配器;找不到则 `ERROR_AND_DIE_FMT("Couldn't allocate object allocator!")`
(`references/FEX/FEXCore/Source/Utils/Allocator/64BitAllocator.cpp:526`)。`CollectMemoryGaps` 还会在遇到第一条
`RegionEnd >= End` 的映射时提前 `return`(`Allocator.cpp:205`),因此一条瞬时的高位 ART 映射就能把收集截断为几段低位小空洞。

**决定性实验(同 FEXCore / 同设备 / 同 4096 页 / `va_bits=39` 稳定):**

| 条件 | 结果 |
|---|---|
| CLI 裸进程 `guest_execution_tests`(`/data/local/tmp`) | 分配器成功,guest reservation `0x7f8000000`、gate `0xfc0000000`,G01…全 PASS |
| app 进程 delay=0(无守卫) | 约 80% 崩溃(0s:崩;抽样 5 次崩 4) |
| app 进程 delay=2s(无守卫,固定 sleep) | 12/12 PASS |
| app 进程 delay=0 + 只找一次空闲槽的探针 | 仍 ~66% 崩(探针与 FEX 看到的空洞不一致) |
| app 进程 delay=0 + **持续静默守卫** | **45/45 PASS** |

结论:空洞**并不缺**(app 自测在 `[4GiB,1<<48/47/42/39)` 各区间都报告 4 个 ≥64MiB 空洞、最大数百 TB),问题是
**ART 在 app 冷启动的头 1–2 秒内爆发式建立/搬移映射(JIT 线程、GC 堆、类加载),与 FEX 的 collect+carve 抢占同一 VA 窗口**;
FEX 的路径是 `ERROR_AND_DIE`,一旦那一瞬空洞被截断就直接 abort,无可恢复返回。等 ART 静默(约 2s 或本守卫的持续静默检测)后
100% 成功。这是 FEX-on-Android 的嵌入时序缺陷,属**主仓适配器**职责(FEX 树禁止 AI 改动)。

## 5. 修复:适配器侧"等待地址空间静默"守卫(本次落地)

`src/core/guest_cpu/fex/fex_context.cpp`,`CreateContext` 内 `SetupHooks` 之前,新增
`WaitForClaimableAllocatorRegion()`(仅 `__ANDROID__`):

- 按 FEX 方式探测 `va_bits`,在 `[4GiB, 1<<va_bits)` 反复尝试 `mmap` 一段**连续 256 MiB**(`PROT_NONE |
  MAP_FIXED_NOREPLACE`)。
- 要求该连续段在 60ms dwell 后仍完整属于自己,并**连续 5 个这样的静默周期 + 至少 300ms 静默地板**才判定 ART 已静默;
  任一周期失败即清零重来。有界(默认 8s),超时返回 false。
- 判定通过后释放探测段,立刻放行 `SetupHooks`。守卫失败时 `CreateContext` 返回结构化
  `ErrorCategory::OutOfMemory` 错误(而非让 FEX abort);正常退出路径不受影响,host 构建完全不走此分支。

这不是靠固定 sleep 掩盖:单次"找到一个空闲槽"探针实测仍会崩(FEX 与探针对空洞的定义不同),必须是**持续静默**
才可靠。首次 `CreateContext` 一次性约 425ms;进程生命周期内只付一次(分配器全局 `call_once`)。

后续可选的更彻底方案(E 级):经 FEX `StealMemoryRegion` / `Create64BitAllocatorWithRegions(Regions)` 显式注入区域,
消除"释放→SetupHooks 重新收集"之间的残余窗口。本守卫已在 45/45 冷启动下无失败,暂不需要。

## 6. 本次为可见性所做的其他永久性改动

- `src/core/guest_cpu/fex/fex_context.cpp`：`GUEST_CPU_DEBUG` 打开时，LogMan Msg/Throw handler 在 `__ANDROID__`
  下同时输出到 logcat（tag `FexCore`）。此前 stderr 在 Android 被丢弃，backend assert 只表现为裸 SIGILL 无消息。
  正常路径无副作用；`guest_cpu_fex` 已 PUBLIC 链接 `log`。
- `android/fex-validation/.../validation_jni.cpp`：`runGuestIncrement` 首次调用前 `setenv("GUEST_CPU_DEBUG","1",0)`，
  使 assert 文本可在真机捕获。
- `MainActivity.kt`：结果同时镜像到 logcat（tag `FexValidation`）并在启动时自动跑 10 次 fixture，便于多屏设备上
  无需 uiautomator 即可采集设备证据。
