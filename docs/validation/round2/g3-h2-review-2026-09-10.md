# H0–H2 复核与 H3 入口结论（2026-09-10）

被审主仓 `56cbc7b1`（H2），前序 `1f8c7a21`（H0）、`0e10defc`（H1）、`470109f6`（本批 G2 修复）。复核时 origin 分支为 `0e10defc04457e019c07fd2a78d4f58d506133b2`，H2 已本地提交但未出现在该远端分支。关联 progress/spec/报告仍有工作区修改及未跟踪文件。本次未修改生产代码、正式测试或子仓。

**结论：H1/H2 的基础调用和 bounded pin 有真实进展，但不能宣布 H0/H2 完成或直接进入 H3。** 三条独立真机探针证明错误后仍有 guest 副作用、native HLE 使用 guest FP 环境、native 异常终止进程；新 case 的 runner 归属再次缺失。下一步按 [修复→H3 执行 spec](../../specs/android-fex-round2-g3-repair-h3.md)推进。

## 1. 已确认的实现进展

- H0 将常规 frame 对应的 fault flag 放到 thread 对象，并在 ExecuteThread 期间登记 frame→weak flag。比旧 context 单 bool 的正常路径归属明确，但仍不带 invocation/错误详情，也未实现即时停止。
- H1 的 syscall operation registry 确实被真实 FEX guest 调用：6 整数、8 整数的两个 spill slot、4 double 返回正例通过，各循环 10 次。
- H2 引入 `GuestBoundedBuffer<T>`，解码 pointer/count，对乘法及地址范围做检查，AcquirePinnedSpan 后持 pin 到当前 HleCallFrame 析构；const 元素表示读，非 const 表示读写。正例 native 收到 3 个元素，写出 sum=60；三种已有坏参数下 native call count 不增。
- `470109f6` 已提交上一轮 G2 源码修复；旧文档所说“e24aad69 加未提交源码”已过期。但 G2 Q1–Q3 尾项未见对应新增实现/证据，不能视作已完成。

## 2. 可行动的审核发现

### R1 / P1：错误只在 Run 结束后上报，后继 guest store 已执行

位置：[HandleSyscall](../../../src/core/guest_cpu/fex/fex_context.cpp#L299)、[BuildRunResultLocked](../../../src/core/guest_cpu/fex/fex_context.cpp#L1507)、[G30](../../../tests/guest_cpu/guest_execution_tests.cpp#L2046)。

HandleSyscall 在 unknown operation 或 adapter 拒绝后设置 fault flag，然后正常返回 JIT。Run 结束时才消费标记、构造 GuestFault。独立汇编 `syscall; mov qword ptr [r12],42; …return gate` 的结果：

| 路径 | native 调用 | sentinel | 最终 Run | 探针退出 |
|---|---:|---:|---|---:|
| unknown operation | 0 | **42**（应为 0） | GuestFault | 2 |
| 已注册但坏 buffer | 0 | **42**（应为 0） | GuestFault | 2 |

这说明“native 未被调用”和“失败后 guest 不再执行”是两项不同的要求，G32b 仅验证前者和最终 StopReason。G30 使用的是 bare HLT，完全不经过新增 HandleSyscall 分支；另一 owner 是 progress loop，也不是合法 HLE。因此其 100 次 PASS 不能验收 R2-H05。

固定 FEX 的非 Windows `DEFAULT_SYSCALL_FLAGS` 没有 BLOCK_END（[X86Tables.h](../../../references/FEX/FEXCore/Source/Interface/Core/X86Tables/X86Tables.h#L412)），[SyscallOp](../../../references/FEX/FEXCore/Source/Interface/Core/OpcodeDispatcher.cpp#L38)仅在 BLOCK_END 时重新读取 RIP。因此简单改 `Frame->State.rip` 或等下个 block 的 interrupt probe，也不能保证同一 block 的 sentinel 不执行。必须证明合法的立即退出路径。

错误记录也不完整：`last_hle_error_` 仍是 context atomic 且没有读出；unknown-frame 仍落到全局 bool，由任意结束的 owner 消费；fault RIP 取最终 RIP，可能已经到 return gate。应记录产生错误时的 thread generation/invocation/operation/guest PC/category，不能事后推测。

### R2 / P1：HLE crossing 保存的是 guest FP 环境，没有装入 host 环境

位置：[HandleSyscall 的 fegetenv/Invoke/fesetenv](../../../src/core/guest_cpu/fex/fex_context.cpp#L339)、[Run 的 host/guest FP 切换](../../../src/core/guest_cpu/fex/fex_context.cpp#L889)。

Run 在进入 JIT 前保存 owner host fenv 并安装 guest MXCSR 对应 FPCR。HandleSyscall 中再次 fegetenv 得到的是此刻 guest 环境，直接 Invoke 后恢复同一份，native HLE 从未获得原 owner host 环境。

真机探针：host=FE_UPWARD（1）、guest=FE_DOWNWARD（2）；native `fegetround()` 返回 **2**，Run 返回后 host 又是 1。外围恢复正确不能证明 crossing 正确。FEX SpillStaticRegs 清 AFP 特殊位，但并不恢复 owner 原舍入模式。

当前 G31 的 double 值都是能精确表示的小数求和，没有检测舍入差异或异常标志。每次 crossing、异常和 callback 层次均需要独立的 host/guest FP 保存恢复。

### R3 / P1：native exception 穿出 HLE 边界，进程直接终止

位置：[adapter->Invoke](../../../src/core/guest_cpu/fex/fex_context.cpp#L344)、[TypedHleCallAdapter::Invoke/Apply](../../../src/core/guest_cpu/hle/call_adapter.h#L350)。

当前没有 HLE exception boundary，也没有完整的异常路径 fenv/owner binding 状态清理。注册一个抛 `std::runtime_error` 的 native HLE 后，真机打印 `libc++abi: terminating due to uncaught exception …`，**exit 134**。本探针在独立进程执行，未影响其他会话。

异常/取消原本属于 H3 后续要求，但在已有真实 native gate 上必须先有最小异常封装，不能让 H3 的嵌套/等待建立在跨 JIT unwind 上。catch 位置必须在返回 JIT 之前，同时覆盖参数解码/分配等可抛路径；转换错误后仍须满足 R1 的立即退出。

### R4 / P1：G30–G32 未接入 runner，新增检查可以失败但不被记账

位置：[SUITE_MAP / ROUND2_MAP / SUITE_OWNERSHIP](../../../scripts/android/run-v0-tests)。这些结构仍止于 G28，R2-H01…H06 映射为空。

对 G30a/b、G31a/b/c、G32a/b 分别合成 `FAIL + exit 0`：每项 `owned=false`、V0 failed=0、R2 failed=0。整进程非零已有 taint 保护；这个事实不能替代逐子项归属。复用现有 runner 单元测试入口得到的 [负例日志](g3-h2-review-2026-09-10/runner-probe.txt)不是实际 guest 执行日志。

### R5 / P1 待定位：当前设备两次完整回归均非全通过

在本次新建目录重编后的同一 binary、AYN Thor API33/4KiB：

- 首轮 202 checks：G24a 一次 FAIL，exit 1。
- 第二轮同 binary：G24b 一次 FAIL，exit 1。
- 仅运行 G24 的诊断副本（增加失败时的 printf）：100 次全部通过，exit 0。

这不足以断言 H2 引入了回归，也不能据后一次局部 PASS 排除问题。原 G24 把大量谓词合并成一个布尔，缺少逐步原因；下一轮应拆出阶段/receipt/timeout/admission/恢复后的进度证据，定位完整套件的交互或时序问题。不得删除失败日志、增加 settle sleep 或无限复跑直到得到一次 PASS。用户原报告来自另一设备/执行环境，本次不能据此宣称原报告造假，但**当前验收未复现全通过**。

### R6 / P2：H1/H2 测试范围和公开契约仍缺项

- H1 仅 4 double，没有 9 double、混合 spill、真正由 guest 指令布置参数/调用栈、callee-saved/red zone 与 invocation 调用日志。现在主要是 host seed 寄存器和 dummy return slot。
- H2 正例 1 次，三个坏参数各 1 次，没有每类 10 次；没有 native 持 pin 时另一 owner remap/protect、只读输出、null/零长、过期 range、错误签名和失败后 sentinel。
- G32 的所谓 overflow count=`0x00ffffffffffffff`，乘以 8 尚不溢出 uint64；目前证明的是范围越界拒绝，不能当成真实乘法 wraparound 测试。实现新增算术 guard 是有价值的，仍需独立边界证据。
- buffer 只有 const/non-const，没有显式 Out/InOut、nullable、最大长度 policy；非 null 零长会 pin 1 byte，需要定义语义。原始 pointer return 仍直接 reinterpret_cast，规范要求的 guest pointer 返回/禁止 host pointer 规则未完成。
- errno/TLS/注册接口的安全类型与生命周期尚未完成。`FexHleRegistryPointer(CpuContext&)` 返回 void* 且 unchecked downcast；这不是已经成型的 backend-free HLE API。

## 3. H3 基础审计

主仓未找到 HleScope、InvokeGuest、WaitingHle/InHle/InCallback 的实现。当前仍是一个 running bool、单 invocation counter、单 `t_binding`，HleCallFrame 没有 owner/context/thread/generation/invocation 身份；普通 Run 的拒绝重入机制应保留。

FEX `Context::HandleCallback` 确实存在，委托到 `ExecuteJITCallback`；它只是底层入口，不是现成的公共 InvokeGuest：

- [Dispatcher callback](../../../references/FEX/FEXCore/Source/Interface/Core/Dispatcher/Dispatcher.cpp#L473)压 host callee-saved、增加 SignalHandlerRefCounter、调整 guest RSP、压 ThunkCallbackRet 并进入 JIT。
- [CallbackReturn](../../../references/FEX/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp#L22)执行特殊的栈恢复和 refcounter 递减，最后返回 thunk；非 Windows 有专门的 FEX reserved opcode dispatch。
- 当前 FexSignalDelegator 的 ThunkCallbackRet 却指向普通 **HLT return gate**。直接调用 HandleCallback 无法由此推导出正确 callback 返回/引用计数清理，更不能推导 inner cancel 的路径。
- ExecuteThread 另会写 ReturningStackLocation；嵌套直接调用还会涉及 host 栈、callret stack、单槽 t_binding/CurrentFrame、signal/FP 状态。仅备份 RegisterFile 不够。

下一 spec 要求先单层 callback 的独立验证，再决定采用 owner 普通栈调度还是 FEX callback 原语；不把“有 HandleCallback”当成“已有 H3 骨架”。
