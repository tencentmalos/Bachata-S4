## 1. 需要处理的问题

### P1：C1 在 C++ 返回后重新 spill，覆盖已经正确保存的 guest GPR

位置：[fex_context.cpp:1061](../../../src/core/guest_cpu/fex/fex_context.cpp#L1061)。变量名与注释都写 non-spill，实际安装的却是 `ThreadStopHandlerAddressSpillSRA`。

真实 FEX 的 [Syscall JIT](../../../references/FEX/FEXCore/Source/Interface/Core/JIT/BranchOps.cpp#L279) 在调用 C++ 前已经保存静态 guest 寄存器；
此后 host 寄存器由 C++ ABI 使用，不能再次解释成 guest 值。[Dispatcher](../../../references/FEX/FEXCore/Source/Interface/Core/Dispatcher/Dispatcher.cpp#L240)
的 spill stop 会重写这些状态，而非 spill stop 直接恢复 dispatcher 保存的 host callee-saved 并返回。两个入口都不替调用方恢复 SP。

真机实测：使用当前正式 adapter、同一 `syscall; store sentinel; return` fixture，给所有 GPR/XMM 注入标记，并在 Run 前验证初始化正确。
Run 返回 GuestFault，sentinel=0，故障 RIP 正确，DestroyThread 成功；**10 个 GPR 错误，且 snapshot validity=0x3f，仍宣称有效**。
错误包括 RSP、RBP、RSI、RDI、R8、R9、R12–R15；其中 R12 从 sentinel 地址变成 1。当前样本的 16 个 XMM、MXCSR、FS/GS 保持。
见 [当前状态探针](g3-c1-review-2026-09-10/device-state_probe.txt)。因此“无崩溃 + sentinel=0”没有证明状态完整。

诊断对照仅对构建目录中的 adapter 副本做 [一行修改](g3-c1-review-2026-09-10/nonspill-diagnostic.patch)：
`ThreadStopHandlerAddressSpillSRA` → `ThreadStopHandlerAddress`，仍在 syscall wrapper 中读取已初始化的 `ReturningStackLocation`。
[同一状态探针](g3-c1-review-2026-09-10/nonspill-state_probe.txt)从 10 处错误变为 0，退出码从 2 变为 0；
[正常 HLE](g3-c1-review-2026-09-10/nonspill-original_probe-good.txt)仍 Returned、rax=1、sentinel=42。
这支持明确根因；不等于已经验证全部 flags/host ABI/FP、异常、循环出口和并发生命周期。

原记录先因 Run 前读取 `ReturningStackLocation=0` 而崩溃，修正读取时机后却保留了排查中切换的 SpillSRA。
两者是独立问题。不能据最初崩溃推断非 spill 入口不兼容，更不能沿用 G1 的 spill 路径：G1 捕获的是活动 JIT 寄存器，syscall wrapper 此时已经执行过 C++。

补充：当前 `RunResult.guest_pc` 为空，但 `fault.guest_rip` 和 snapshot RIP 正确。它是 optional 字段，本报告不据此单独判错；
新的状态探针显式验证 `fault.guest_rip`，不沿用原探针对两个 PC 的宽松 OR。初版额外要求 guest_pc 的日志也保留并注明修正。

### P2：旧 Release 完成前允许换代，其迟到写入会污染新代

位置：[test_run_gate.h:83](../../../src/core/guest_cpu/fex/test_run_gate.h#L83)，关联 `Arm` 第 48–50 行与 `WaitAtEntry` 第 109–114 行。

新实现确实增加了票据、在 Arrived/Releasing 阶段拒绝 Arm，并去除了懒初始化。这些改进成立。
但 owner 将 phase 设成 Idle 后，旧 Release 仍可能在 condition_variable 等待中。此时新 Arm 清空了共用的 clean/result/decided 字段。
旧 Release 的谓词要求“当前 phase=Idle 且 last_exited=旧票据”，新代进入 Armed/Arrived 后它会超时；
随后它不复核 generation，就把 false 写入新代的 release_decided/result。新代 Release 因此直接返回 false，不再释放 owner。

[公共 API 并发探针](g3-c1-review-2026-09-10/gate-race-probe.cpp)直接 include 当前正式共享 header，没有复制协议或改私有状态。
本次第 1 轮即复现：`owner1_clean=1, release1=0, release2=0, owner2_clean=0`，见 [日志](g3-c1-review-2026-09-10/gate-race.txt)。
这属于 test helper 缺陷，不是生产 Pause 中断的反例。

修正应让终态结果归属于具体票据，旧 waiter 不能写下一代的可变字段。可以延后允许重 Arm 的时机，也可以让 waiter 持有独立的代次结果；
同时定义并发重复 Release 的一致结果。现有测试只覆盖顺序重复 Release 和释放前的 re-arm，漏了这个交错。
其 `200 次 yield` 也不是可靠的到达超时，应改为有真实 deadline 的握手；不应靠大量重复全套 guest 测试替代协议反例。

### P2：gate owner 超时后 Run 收尾仍未处理 pending receipt

位置：[fex_context.cpp:1025](../../../src/core/guest_cpu/fex/fex_context.cpp#L1025)。失败分支只清 `running` 并返回 BackendFailure，
绕过后续 interrupt page 复原、stopped snapshot/receipt 发布与通知。B1 对这条路径的要求仍未完成。

[真机探针](g3-c1-review-2026-09-10/timeout-probe.cpp)先等待 Arrived，再 RequestInterrupt(Pause)，不 Release，等待 owner 的 Run future 真正结束。
结果见 [日志](g3-c1-review-2026-09-10/device-timeout_probe.txt)：Run 报 test entry gate timed out，gate Exited=true；
随后两次 WaitStopped 都报“owner has not stopped”。execution lease 已能重新获取，owner 最终能够销毁。
即：RAII lease/owner 销毁部分可用，但请求端状态没有完成收尾。页保护未复原是源码结论，本探针没有直接读该页权限。

修正需明确 BackendFailure 的 stop/receipt 语义，收尾保护页、pending requests、snapshot、last_reason 和通知；
控制端最终应得到故障终态或明确退休错误，不能在已结束的 Run 上反复等待。补 owner timeout + controller request，以及失败 drain retry 的真实 adapter 回归。
