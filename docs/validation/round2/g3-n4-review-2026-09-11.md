- `FexSyscallWrapper` 已在每次正式 Run 安装；stop 地址归属 owner binding，采用非 spill 入口，并在 syscall 时读取有效的 ReturningStackLocation。
  tests=OFF 的新 Release 构建仍包含生产 wrapper，gate/trace 匹配符号为0。不能再沿用“shim 默认关闭”的旧状态描述。
- [unknown 状态探针](g3-n4-review-2026-09-11/hle_probe-unknown.txt)注入并验证初始化后，16 GPR和16 XMM全部匹配；
  GuestFault、sentinel=0、fault RIP正确、host舍入模式在Run返回后恢复。原10-GPR缺陷可以关闭。
- G33/G34/G35/G32c 已进入正式 guest suite。单次 unknown、错误后loop、registered拒绝抑制后继，以及串行新thread/recreate不继承错误有证据。
- 原先旧 Release 污染新 Arm 的 [公共API反例](g3-n4-review-2026-09-11/gate-old-race.txt)本次100次内未再复现；源码已把迟到结果与新代字段隔开。
  这不等于整个 gate 协议已正确，见下面两个确定反例。
- gate超时且**已经有 pending Pause**时，[真机结果](g3-n4-review-2026-09-11/gate_timeout_probe-pending.txt)确实能够正常返回 PauseRequested、发布receipt，guest progress保持0。

## 2. 实现与验收问题

### P1：合法 HLE 的参数正规化仍覆盖 RCX 架构状态

位置：[fex_context.cpp:435](../../../src/core/guest_cpu/fex/fex_context.cpp#L435)及[第447行](../../../src/core/guest_cpu/fex/fex_context.cpp#L447)。
R10→RCX 是给 adapter 的第四整数参数视图；将这份完整 RegisterFile 写回 FEX State，又把参数值当成 syscall 后的 RCX。

[真实 valid probe](g3-n4-review-2026-09-11/hle_probe-valid.txt)中，native `40+1` 正确返回41，sentinel=42、Returned，
但 RCX 应为 syscall successor `0x7f8010002`，实际为 R10 标记 `0x1234000a`。只有这一个 GPR 不匹配，probe exit2。
这是旧 spec 已指出、现在仍未完成的修复；G33b只检查sentinel，未验证返回值与架构状态，无法阻止回归。
应隔离参数视图，仅回写约定返回字段，补正常HLE后的RCX/R11、RSP、callee-saved和状态有效位断言。

### P1：native FP 环境和异常边界仍未实现

位置：[fex_context.cpp:440](../../../src/core/guest_cpu/fex/fex_context.cpp#L440)。此处 fegetenv 获取的是正在运行的 guest 环境，
没有在 native 入口前装入 Run 保存的真正 owner host 环境；`adapter->Invoke` 周围也没有异常边界。

- [FP probe](g3-n4-review-2026-09-11/hle_probe-fp.txt)：host设FE_UPWARD、guest设FE_DOWNWARD，native读取到后者；Run结束后host恢复了，不能据此宣称crossing正确。
- [throw probe](g3-n4-review-2026-09-11/hle_probe-throw.txt)：native抛std::runtime_error，进程exit134，libc++abi报告未捕获异常。
  当前测试没有走到可清理的GuestFault返回。这是隔离CLI测试进程，不是APK故障实测。

这两项在执行记录中也承认为后续R2，不能算本轮新引入的回归；但它们仍是完整HLE/APK验收前必须修的真实缺口。
需覆盖decode/pin/native/return encoding全部C++作用域的FP/errno/异常清理；不允许跨JIT unwind。

### P2：gate 超时在没有 pending 请求时放行了无限 guest

位置：[fex_context.cpp:1058](../../../src/core/guest_cpu/fex/fex_context.cpp#L1058)。超时分支现在只打印日志后进入JIT；它依赖尚未验证的前提“控制端一定已发中断”。

[无pending真机反例](g3-n4-review-2026-09-11/gate_timeout_probe-no-pending.txt)：Arm后不Release，也不发Pause；
超过5秒gate已Exited，6.5秒时Run仍未返回，progress已经推进731358055。审核probe随后主动Cancel完成清理，不能算超时路径自行成功。
因此只修好了“有pending Pause”的旧反例，不能说owner timeout已完整关闭。

应在超时后走定义明确的停止/失败收尾，保持页保护、snapshot、receipt、lease一致；不能把超时当成执行授权。
若复用现有stop机制，内部失败请求必须明确归属且不吞外部请求，并证明guest零推进；不能只依赖可能不存在的pending位。

另有[无需并发的协议反例](g3-n4-review-2026-09-11/gate-early.txt)：Release-before-Arrived返回false，owner却返回clean=true；
同票据的重复Release在新Arm前为false、新Arm后变true。原因是[第74–80行](../../../src/core/guest_cpu/fex/test_run_gate.h#L74)把错误也写成release_requested，
owner随后把它归档为成功。应区分release/abort/timeout，当前态和历史态共享同一终态含义。
这些均为test helper问题，不是生产Pause的故障结论；正式协议测试仍通过，说明负例覆盖不足。

### P2：当前 runner 自测有两条失败，无法复现“22/22”

直接运行仓库当前测试得到22个test methods、2个失败，exit1，见[原始日志](g3-n4-review-2026-09-11/runner-unit.txt)：

1. 新增G32c后输入已有8个失败子项，[测试第236行](../../../tests/guest_cpu/test_v0_runner.py#L236)仍断言7。runner实际去重计数8在这里是正确的。
2. G34在ROUND2_MAP中，却漏在[SUITE_OWNERSHIP](../../../scripts/android/run-v0-tests#L310)，现有ownership断言直接失败。

accounting21/21仍通过；本次未复现之前“直接checker FAIL却exit0”的旧缺陷。
不能通过删断言消除失败，应修登记/测试输入期望并增加表间完整性校验。最终提交需重新运行自测，不能引用较早时点的PASS。

### P2：H05 并发与错误生命周期矩阵被高估

[G36](../../../tests/guest_cpu/guest_execution_tests.cpp#L2602)的健康owner执行**不含syscall的progress loop**。
它证明错误owner没有拖停另一条活动JIT，尚未验证“两owner同时进入真实HLE”的参数、buffer、TLS、错误隔离。
G35全部在主host线程串行CreateThread/Run，覆盖的是不同guest thread实例，不能补上这个并发缺口。

仍缺：unknown/rejected/合法HLE/错误后loop各100次；两owner合法/错误HLE重叠100轮；Fault与Pause/Cancel/Shutdown明确交错；
部分参数已pin、后续参数失败的基线；fault后Run/Resume与旧身份生命周期负例。G32c首个buffer立即失败，没有测“先pin后失败”。
这些在[N4原表](../../specs/android-fex-round2-g3-r0-exit-next.md)中是验收项，不能降为可略过的“边角”。
G33a也未断言StopReason，G33b未断言返回值，G36的WaitStopped用1ms并直接.Value()；应完善失败诊断和有界清理。

结构化事件是进展，但仍与per-thread bool/context全局fallback并存。
[null/未登记frame](../../../src/core/guest_cpu/fex/fex_context.cpp#L410)仍设置unknown_thread_syscall_，
[第1729行附近](../../../src/core/guest_cpu/fex/fex_context.cpp#L1729)仍由任意下一次BuildRunResult消费。
本次没有从公共正常调用复现null/未登记frame；这是明确未完成的N4异常生命周期策略，不能据此声称正常并发已经串错。
参数拒绝的具体信息也没有完整进入事件，last_hle_error_仍是context原子槽；需要定义可归属事件及不可归属时的context失败处理。

## 4. 到 APK 的推进结论

分两条相互汇合的工作线，详见[新执行spec](../../specs/android-fex-round2-n4-to-apk.md)：

- CPU线：runner/gate修复 → N4完整矩阵与RCX/FP/异常/ABI → 单层callback证明 → HleScope/两层嵌套/WaitingHle → G2交叉。
- App线：尽早构建最小普通APK，链接同一guest_cpu_fex与Foundation DebugBus → JNI/ART/session/信号/依赖闭包 → 完整G4。

首个APK只承诺安装、加载、进程内4KiB/身份检查、基础guest输入输出与Stop。
完整APK验收要求Swan/API36/普通app身份重跑规定CPU/HLE/VM矩阵、生命周期、Foundation、只读snapshot与10分钟soak。
SDK36在本机存在，NDK实际metadata仍只到35；native API与app SDK分别锁定，遵守Round2对native API35的明确许可，不能伪造API36 sysroot。
首次APK和最终ROUND2_ACCEPTED分开记录，V0仍IN_PROGRESS；游戏加载/图形/VR属于后续里程碑。
