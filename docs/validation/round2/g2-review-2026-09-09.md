# G2 进展复核（2026-09-09）

**结论：G2 需要修复，不能按当前实现直接进入 G3。** 审核对象是已推送的 `5304e5a9831a4d6ccbaa776b854685332f26d23b`；远端 `origin/codex/android-fex-round2` 当次查询与本地 HEAD 一致。G1 已在 `50b27016` / `f37ad9cf` 固化，G2 增加了协调、token reprotect/remap 和 ClearCodeCache 的接口，但实现和验证未满足完整 G2 契约。

本次从独立 embedder 构建目录重编被审主仓代码，复用固定 FEX 静态库，重新在 Pocket DS / API 33 / ARM64 / 4 KiB 上运行：原 guest suite **85/85**、device contract **37/37**；macOS host contract **36 PASS + 1 SKIP**。这些原有结果可以复现。随后通过独立探针复现下面的错误，说明通过的测试未覆盖关键路径。**本轮没有修补生产实现来改变审核结果，也没有修改子仓。**

源码身份、实际部署 binary SHA/Build ID、设备信息、探针和原始输出在 [证据目录](g2-review-2026-09-09/README.md)。CLI 仍不代表 Swan Android 16 普通 APK 验收。

## 1. P1：ClearCodeCache 未取得 FEX 失效锁，真实调用后会挂起

位置：[fex_context.cpp](../../../src/core/guest_cpu/fex/fex_context.cpp)，`ClearCodeCache` 的直接 `InvalidateCodeBuffersCodeRange` 调用；对照同文件已存在的 `DiscardTranslationsImpl`。

FEX pinned [Core.cpp:1070](https://github.com/tencentmalos/FEX/blob/385a0cc4d81cd456c8d5c26b4f09cb5a7d8d5842/FEXCore/Source/Interface/Core/Core.cpp#L1070) 明确要求调用者持有 `GetCodeInvalidationMutex()`。检查表达式 `CodeInvalidationMutex.try_lock() == false` 在 `ENABLE_ASSERTIONS=OFF` 下仍会由 [LogManager.h](https://github.com/tencentmalos/FEX/blob/385a0cc4d81cd456c8d5c26b4f09cb5a7d8d5842/FEXCore/include/FEXCore/Utils/LogManager.h#L70) 的 `(void)(pred)` 求值。没有先加锁时，try_lock 会取得 mutex，而新入口没有对应解锁。旧实现已正确使用 scoped lock，并分别处理共享 cache 和每线程 cache，新入口绕过了它。

[clear_rx.txt](g2-review-2026-09-09/clear_rx.txt)：先真实执行 A，持正确 token 在 RX mapping 上 Clear，打印 `clear_RX_returned=1`；紧接着调用普通 InvalidateCode，**3 秒 timeout / exit 124**。这个实际路径和源码契合，不能再把挂起归因为“0..2^36 清到了 FEX host 内部区域”。该 FEX 方法按 **guest 地址**在 CodePages 索引中查找，不等同于 munmap host 内存；原先的大范围猜测没有成立的证据。

修复要求：统一采用正确失效协议，验证锁平衡和后续重新编译；不能通过跳过调用消除挂起。

## 2. P1：ClearCodeCache 不完整清理，还接受别的 address space 的 token

当前入口只查 `token.IsValid()`，没有校验所属 space、活动 epoch、context 协调状态、实际 running owner。它只清当前有 Execute 权限的 mapping，也没有调用每线程 `InvalidateThreadCachedCodeRange`，后者还负责 decoder range cache / call-return cache。

两个独立复现：

- [foreign.txt](g2-review-2026-09-09/foreign.txt)：另一个 address space 的有效 token 被接受，`foreign_token_accepted=1`。该 token 没有停止被清理 context 的线程，不能提供安全授权。
- [rw_skip.txt](g2-review-2026-09-09/rw_skip.txt)：同一个 guest thread 已执行 A=17；持 token remap 同 VA 为 RW，写入 B 字节，然后调用 **ClearCodeCache**，再 RX、复用旧 thread 执行。Clear 报成功，实际仍返回 **17，预期 34**。探针刻意不用 PublishCode 的额外失效替 Clear 掩盖错误。

G22 在 RW 状态调用 Clear，代码 mapping 恰好被筛掉；后面的正确结果由 PublishCode 的失效和新建 thread 取得，不能证明 Clear 工作。需要覆盖曾经执行但当前 RW/已移除的范围、返回 gate 等后端拥有的代码，以及共享/线程本地缓存。

## 3. P1：QuiesceContext 停止阶段尚未关闭准入，失败后也没有保持关闭

位置：`fex_context.cpp:900–948`。先快照 thread 集合，再逐个 Request/Wait；直到最后才调用 `space_.Quiesce(..., true)`。此前没有 context 协调 gate。`Resume` 仅检查 `IsQuiescent()`，同样无法覆盖停止阶段。每个等待还重新使用完整 timeout，而非共享 deadline。

[admission.txt](g2-review-2026-09-09/admission.txt) 用有界 native hold 保持已有 owner 未 ack：

```text
coordinator_still_waiting=1
admission_closed_while_stopping=0
create_admitted_while_stopping=1
quiesce_timed_out=1
execution_admitted_after_timeout=1
```

因此函数注释中“原子关闭 Run/CreateThread/Resume”“失败保持 closed”与实际行为不符。新 owner 可错过快照，已停止 owner 也可重新 Run，最后 drain 会等待一个没有收到停止请求的线程。它未必导致带活跃 lease 的 token 被错误授予，但已破坏协调协议、失败语义和时间预算。

## 4. P1：协调者清空全部 pending，吞掉外部 Cancel

位置：`fex_context.cpp:935–942`，收到回执后直接 `interrupt->pending = 0`，并未只消费属于本事务的 pause，也未走完整 ticket/receipt 的消费过程。

[cancel.txt](g2-review-2026-09-09/cancel.txt)：两个 owner 都实际收到外部 Cancel 并返回 Cancelled；协调成功、释放 token 后，直接下一次 Run，**至少一个 owner 在没有 Resume 的情况下又更新了 guest counter**：

```text
both_original_runs_cancelled=1
cancelled_owner_reexecuted_without_resume=1
```

这是对 G1 请求保留语义的回退。必须按请求来源/epoch 保留用户 Pause、Cancel、Shutdown，且 fault 不得被当作普通事务 pause。

## 5. P1：token 新 mutator 绕过 sink 排他，能让成功发布的字节消失

位置：`address_space.cpp:998–1097` 的 ReprotectUnderToken / RemapUnderToken。它们检查 token 和 pin，却没有检查正在执行/排空的 sink；旧 PublishCode 在调用 sink 时会临时释放 address-space lock。

[sink-race.txt](g2-review-2026-09-09/sink-race.txt)：同一 token 下，一个线程 PublishCode 写入 0x5A 后停在有 barrier 的 sink，另一个线程 remap/reprotect；两个新 mutator 都成功。随后 sink 成功返回，PublishCode 也报告成功，但读回字节已是 remap 后的 **0**，不是 **0x5A**。已有 token 不代表可以穿过当前正在执行的 publication 回调。

此外 [poison-remap.txt](g2-review-2026-09-09/poison-remap.txt) 证明：PublishCode 失败且仍有 poison 时，RemapUnderToken(RX) 成功赋予 Execute；Reprotect 的 poison 拒绝未复制到 Remap。**现有全局 poison admission 仍阻止 Run，探针没有证明 CPU 已绕过该全局保护**，但页面权限不变量已经破坏。

修复时统一校验 sink in-flight/draining、pin、token provenance/epoch、poison、dirty generation 和 mutation 状态；真实 mmap/mprotect 失败后的 backing/metadata/poison 状态也需要注入测试。

## 6. P1：G21/G22 未覆盖它们声称的 owner/缓存生命周期

`guest_execution_tests.cpp:1275–1289, 1300–1332` 清楚显示：G21 的 Quiesce 时没有活跃 owner；`run_constant` 在主 host 线程上按顺序 CreateThread→Run→DestroyThread。两次调用甚至不是两个 native owner；只是两个 guest_tid。G22 使用相同模式，并非注释说的“复用两个 owner”。

G20 确实证明一次双 owner 协调停止，但没有修改代码；不能把它和 G21 的串行 fresh-thread 发布拼接成“100 次同一双 owner 在旧版本运行→停止→新版本恢复”。Clear 在 G22 还是 no-op，M21–M23 host case 也没有调用 CPU Clear、更没有注入真实 remap syscall 失败。

下一阶段必须用持久 owner 和 thread handle、带版本的循环 fixture，在每轮停止前后直接观察两个 guest 的输出，不得通过销毁 thread 消除本地 cache 证据。

## 7. 进度口径和文档来源纠正

我上一版 [G2 handoff](../../specs/android-fex-round2-g2-handoff.md) §2 将 M02 写成 remap、M03 写成 Clear，确实与主 spec 冲突，是此次范围漂移的一个来源。此次已更正，不能只要求执行者负责。主 spec 的规范定义一直是：

| 规范 ID | 正确范围 | 当前审核判断 |
|---|---|---|
| R2-M01 | 同一双 owner 运行 A，协调停止、patch B、恢复，100 epochs | 未达到；G21 使用无运行 owner / 串行新 thread |
| R2-M02 | 整个 quiesce 的准入、pin/WaitingHle/迟到请求/sink 竞争、timeout 与外部请求保留 | 已复现准入和 Cancel 错误；WaitingHle 还须 G3 合并验证 |
| R2-M03 | token remap 同 VA，复用 thread，Clear 后状态不变且执行新代码，removed range 查询撤销 | 已复现 Clear 挂起/旧译码；FEX executable_ranges 仍为 append-only，未做移除/权限同步 |
| R2-M04 | guest store 修改已执行代码，经协调者/真实 HLE 发布再执行 | 未开始；host 协调子路径可以先做，真实 HLE 部分并入 G3 |

`progress.md`/AGENTS 仍停留 G1，仓库没有新 G2 原始运行日志/24 项结果；G20–G22、M21–M23 尚未加入 runner 的映射和 ownership。还有一个 G1 evidence 回归文件 `tests/runner/test-g1-evidence.py` 仍 untracked，此前“G1 全部固化”需补核对。不能用当前 85 这个 suite 总数推算 R2 通过项。
