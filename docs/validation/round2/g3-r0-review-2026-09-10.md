## 2. 尚需处理的问题

### P1：R2 专属失败可见于 JSON，仍被 runner 当作成功退出

位置：[run-v0-tests](../../../scripts/android/run-v0-tests#L1015)、[最终返回](../../../scripts/android/run-v0-tests#L1109)。`total_failed = failed + accounting_errors` 中 `failed` 仅统计 V0；已被 ROUND2_MAP 消费的失败不会进入 orphan 列表，R2 报告又到构建JSON时才计算，因此R2-only失败不影响退出码。

本次用实际 parser、ownership、聚合器和 `main()`，只替换设备/构建检查入口，独立注入：

| 输入 | R2结果 | runner返回 |
|---|---|---|
| G30a/G30b 各自 FAIL，suite exit0 | R2-C03 FAIL | **0** |
| G31a/G31b/G31c 各自 FAIL，suite exit0 | R2-H01 FAIL | **0** |
| G32a/G32b 各自 FAIL，suite exit0 | R2-H02 FAIL | **0** |
| G31a FAIL 后同ID PASS，suite exit0 | R2-H01 FAIL | **0** |
| 未映射 Z99a FAIL，suite exit0 | orphan FAIL | 1 |

七项的 V0 `summary.failed` 都为0。这一字段可以继续保留V0范围，但必须另有覆盖全部实际失败的总状态/计数，并控制CLI退出码。当前 release_status 恰好仍是 V0_IN_PROGRESS，是因为其他未完成项；不能据此认定失败出口正确。CI只检查exit时会漏掉已映射的HLE回归。

来源：[自测 run_runner](../../../scripts/android/test-runner-accounting#L49)丢掉了 `subprocess.run` 的返回值；新增第10条只断言R2-H01 JSON为FAIL。因此“15/15通过”和此漏洞同时成立。独立探针的全部输入、输出、返回码见 [runner/summary.json](g3-r0-review-2026-09-10/runner/summary.json)。另用host合成输出fixture运行真正runner子进程，G31a FAIL仍得到R2-H01 FAIL/进程exit0，见 [process记录](g3-r0-review-2026-09-10/runner-process/run.json)；此项只验parser/聚合/进程出口，不证明guest执行或suite来源。

修复要求：V0、R2、unmapped/失败suite分别记账，统一决定整体失败与非零返回；不要把同一子项在多个父项下的数量混成独立失败数量。自测必须断言真正runner进程返回码，至少对全部G30–G32逐项覆盖FAIL+exit0、重复冲突、missing/SKIP、crash/timeout及正常partial结果。

### P2：G24 稳定性过滤不能证明冻结点无锁，具体锁根因尚未确认

位置：[TestCoordinatorRecovery](../../../tests/guest_cpu/guest_execution_tests.cpp#L2392)和 [定位记录§3–5](g3-g24-localization-2026-09-10.md)。目前 SIGUSR1 仍会落到任意host PC；过滤只要求 second 的 progress **至少变一次**，并非文档所说的“持续推进”或“已在确定无锁点”。

两条代码事实足以否定这一推论：

1. [WritePriorityMutex::lock_shared](../../../references/FEX/FEXCore/include/FEXCore/Utils/WritePriorityMutex.h#L143)在没有writer-owned/writer-waiting时允许多个reader同时持锁。仅冻结一个读锁持有者并不会阻止另一reader推进。现有诊断没有记录所谓排队writer的身份或锁状态。
2. [ExitFunctionLink](../../../references/FEX/FEXCore/Source/Interface/Core/JIT/JIT.cpp#L531)会把调用点直接链接到目标block；已链接热循环能继续执行，不必每轮取得同一锁。因此“second推进了一次”无法证明 held owner 没持有second将来停止/退出时需要的锁。

历史 `w104.txt` / `s212.txt` 确实记录到 second progress未推进、wchan=futex_wait_queue_me；它们只能证明观测时存在futex等待，**不能识别具体mutex、等待者/持有者、signal落点或中断是否已经服务**。例如guest已经停下但Run尾部等待锁，也会没有guest progress。`Await` 在释放后成功也没有测量“立即”完成。故“精确根因就是CodeInvalidationMutex读锁+排队writer”“已排除中断未服务”“已证明生产路径无关”均应降为待验证假设。

此外，[重试释放循环](../../../tests/guest_cpu/guest_execution_tests.cpp#L2421)等owner progress最多1秒，**超时后没有拒绝/断言就再次清标志、发signal**。当前没有记录handler退出代次；进度观察还可能读到采样间隙发生的变化，不能严格证明上一次handler已退出。该问题是握手协议不完整，不是本次已复现的新挂死。

本次完整suite通过，60份历史PASS日志也真实存在；这些支持过滤降低了现象发生率，不能替代确定测试同步条件。建议在主仓test-only seam构造“已登记running且保留执行lease、尚未进入JIT、所有相关锁已释放”的延迟应答点，使用到达/释放/退出的代次握手。保留真实JIT中的G1中断测试，不能用这个host阶段用例替代它们。若仍要保留任意PC冻结，必须采集PC/stack/锁地址等证据再声称精确根因。

## 3. R1–R3 与 H3 的真实进度

本轮生产源码和FEX静态库未改。上一 [H2复核](g3-h2-review-2026-09-10.md)的三条生产故障没有修复，本次不冒称再次运行那些探针：

- unknown/rejected syscall只置fault flag并返回JIT，最终虽报GuestFault，后继sentinel已写42；错误后忙循环缺少立即退出保证。
- native HLE看到guest FP舍入，owner进入guest之前保存的host fenv尚未进入每次crossing。
- native exception没有在C++ HLE边界捕获，上次独立探针exit134；pin/FP/错误事件清理未完整验收。

H1六/八整数、四double，以及H2 bounded pin/sum60是可运行的基础。完整guest构栈ABI、真实溢出、buffer policy、errno/TLS、有类型registry仍为R3。HleScope/InvokeGuest/WaitingHle仍没有主仓实现，不能跳过R1–R3直接叠加嵌套dispatcher。

G2 Q1–Q3、G4普通APK/JNI/ART/package闭包继续显式待办。4KiB为当前目标；16KiB、finite Step、Vulkan、游戏和VR不扩入本阶段。
