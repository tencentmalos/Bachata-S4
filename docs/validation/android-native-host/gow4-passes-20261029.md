## TAA is present; this resolve does not upscale

Compute shader `0x2b5ba6df` runs exactly once in each interval (actions3059 and6120),
dispatch240×135×1. All five image descriptors are1920×1080:

| Role inferred from the data flow | Flip286 | Flip287 |
|---|---|---|
| Current composited color, RGB10A2 |`0x223b18000`|`0x224310000`|
| Single-channel auxiliary input |`0x2238d8000`|same|
| Two-channel displacement input, RG16F |`0x21b748000`|same|
| Prior accumulated color, RGB10A2 |`0x225300000`|`0x224b08000`|
| New accumulated color, RGB10A2 |`0x224b08000`|`0x225300000`|

Thus the first frame's output is the second frame's history input. The immediately
following full-screen draw (FS`0x1ec2004d`) samples that output. Exact600-dword GCN
was extracted from this capture and decoded with `tools/gcn-disasm`:

- `0x1d4`: load a two-component displacement; `0x214/0x21c`: add it to normalized
  current-pixel coordinates before history sampling.
- `0x224–0x3ac`: polynomial filter weights and five history samples.
- `0x618–0x6b0`: nine-sample moments, variance/square root, and median clamping to
  mean±scaled deviation.
- `0x8d4–0x93c`: history/current difference, adaptive blend and color conversion;
  `0x954`: write the accumulated output.

This is strong instruction/data-flow evidence of TAA with history rejection/clamping.
It is **one temporal resolve**, not dozens of TAA passes. Equal input/output dimensions
do not support temporal upscaling or4K checkerboard reconstruction in this captured
1080p mode. This does not characterize every console mode or every scene.

There is another half-resolution temporal chain: shader`0x7605787f` reads
`0x21a130000` then writes`0x219cb0000` in flip286; these swap in flip287. It also
produces480×270 and240×135 images followed by horizontal/vertical filtering.
Its exact effect name remains unproven; do not call every history texture TAA.

Host reconstruction is a separate question. Live `xr_render status` reports
`upscaler=0`, `draws=0`, `scope=host-presentation`. Although saved global
`gpu.fsr_enabled=true`, Android Presenter disables the desktop FSR path and uses the
separate spatial options for its direct path. Current host FSR/SGSR is **off**.

## Other large workloads and scale coverage

The two most frequent compute shaders are`0xe7a719c7`(227 calls) and`0xd92dd2ba`
(157 calls):384/598≈64.2% of dispatch actions in flip286. They read/write several
240×135×128 3D volumes using small10×8/9×2 dispatch grids, with3D history volumes and
other inputs. This is volume processing, not full-screen TAA. Counts are not GPU
cost, and each dispatch must not be described as writing the entire volume. The
precise effect name and cost remain to be established. Their read-only buffer
descriptor includes a4GiB-minus16 range, relevant to the existing upload/tracking
hotspot but not proof that all those bytes are copied on every dispatch.

Only287/2464 graphics actions (11.65%) have all attachments at75% scale. Main
1920×1080 depth/G-buffer targets and an8192×4096 depth atlas remain native.
The final guest display target is scaled to1440×810. Log evidence includes fragment
buffer writes (`0xd2a7adbc`), fragment image writes (`0xa78f6982`) and consequent
mixed-attachment/native promotions. Therefore the75% setting does not reduce the
majority of draw targets. This is coverage, not a pixel-time percentage. Forcing
these images to scale without adapting exact accesses/side effects risks corruption.

Optimization priority: reduce CPU upload/tracking and synchronization overhead,
understand storage side effects before extending scaling, and measure the volume
workload. Do not disable TAA, volume passes, readbacks or barriers merely from counts.
