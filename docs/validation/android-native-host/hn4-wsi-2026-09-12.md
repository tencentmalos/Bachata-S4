## Changes

### vk_swapchain.{h,cpp} (core)

1. **Bounded acquire + stop flag.** `AcquireNextImage()` replaced the
   `std::numeric_limits<u64>::max()` (infinite) timeout with a 100 ms bounded
   `acquireNextImageKHR` in a loop that re-checks a new `std::atomic<bool>
   stop_requested`. `eTimeout`/`eNotReady` → loop (acquire already waited, so no
   busy-spin); `RequestStop()` (new public, thread-safe) makes the loop return
   `false` promptly so teardown / surface detach never wedges on a blocked acquire.
   This is the one weakness the reference research flagged in both azahar and
   citron (both use UINT64_MAX) and that spec HN4 requires fixed.
2. **Rebuild the VkSurfaceKHR on surface loss.** `AcquireNextImage`/`Present` now
   set a `surface_lost` flag on `eErrorSurfaceLostKHR` (distinct from out-of-date/
   suboptimal). `Recreate()` checks it and calls the new `RebuildSurface()` first:
   `waitIdle` → `Destroy()` → `destroySurfaceKHR(old)` → `surface = CreateSurface(
   instance, window)` (reads the window's current `ANativeWindow*` from
   `window_info.render_surface`) → `FindPresentFormat`/`FindPresentMode` for the
   new surface → then the normal swapchain `Create()`. Previously `Create()` always
   reused the same `surface` and could never recover from a real Android surface
   loss (backgrounding/rotation hands back a fresh Surface). Desktop never sets
   `surface_lost`, so its path is byte-for-byte unchanged.
3. **Android identity preTransform.** `SetSurfaceProperties()` already preferred
   `eIdentity`; added a comment documenting why it matters on Android (the
   compositor's `currentTransform` is often rotated; the frontend owns orientation,
   matching azahar/citron), no behavior change.

### vk_presenter.cpp (thin)

`~Presenter()` now calls `swapchain.RequestStop()` first, so any acquire that is or
becomes blocked releases and teardown proceeds. The existing acquire-retry block
(Recreate → retry → skip frame) is already bounded and needs no change: with the
stop flag short-circuiting acquire, both retries return quickly and the frame is
skipped — no infinite recreate loop.

Present-thread fact (corrected): the present thread is
`Libraries::VideoOut::VideoOutDriver::present_thread` (a `std::jthread`), whose loop
calls `Presenter::Present` → `Swapchain::AcquireNextImage`/`Present`
**synchronously** and checks `token.stop_requested()` every iteration. So the
bounded acquire is what actually lets that loop observe its stop token and exit:
with the old `UINT64_MAX` a wedged surface would block the loop forever regardless
of the token. The 100 ms bound caps teardown latency even without `RequestStop()`;
`RequestStop()` makes it instant. azahar's async `next_surface`/`recreate_surface_cv`
handoff is still unnecessary — there is one consumer (the present thread) and it is
the thread that recreates.

### vk_platform.cpp

Android surface creation (`vkCreateAndroidSurfaceKHR` from `ANativeWindow*`,
`VK_KHR_android_surface`) already landed in `75035817`; reused unchanged.

## Deferred to HN5 (needs a frame-producing driver + device)

- On-device **WSI_PASS**: real clear/triangle 300 frames, 20× Surface
  disconnect/recreate/rotate including Stop-during-acquire, no old-generation
  present, no dangling reference. Needs a minimal render driver (or the real guest
  renderer) — none exists yet.
- The **app-side Surface handoff**: the JNI adapter that calls
  `ANativeWindow_fromSurface` on the UI thread and stores the `ANativeWindow*` into
  `window_info.render_surface` (with release-old-window on change). This batch does
  the renderer-side seam that *consumes* `render_surface`; the Java Surface → native
  plumbing is the HN5 integration step.
- **Full `WindowSystemInfo` decoupling** from `Frontend::WindowSDL&`. Swapchain/
  Presenter still take `WindowSDL&` (reading only `GetWindowInfo()`/`GetWidth/
  Height`); `ImGui::Core::Initialize` also takes `WindowSDL&`, so a clean cut has a
  wide blast radius and can't be desktop-full-build-verified here. The Android WSI
  path already only consumes the opaque `render_surface`; the hard-dependency
  removal is a separate refactor. A designed superset (a `WindowSurfaceProvider`
  seam in a new `window_system_info.h`, moving `ImGui::Core::Initialize` out of the
  Swapchain ctor into the Presenter, and a **surface-generation** counter so a
  *new* `ANativeWindow*` is detected without needing an `eErrorSurfaceLostKHR`) is
  the recommended HN5 form; this batch keeps the minimal `surface_lost`-driven
  rebuild the approved plan scoped.

## Risks

- Real SurfaceLost/rotation behavior is only validatable on device (HN5); this
  batch guarantees the code path and compilation, not runtime recovery.
- The bounded-acquire stop flag is most load-bearing once a present thread exists
  (HN5) or on app backgrounding; with today's synchronous present it is correct but
  lightly exercised.
