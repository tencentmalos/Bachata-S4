# A8XX GPU 的 CP 读到全零：测试进度报告（2026-10-19）

本文汇总截至 2026-10-19 晚的测试结果，供交接或对外说明。完整过程、原始数据和每一轮的细节见 [A8XX DDE 记录](a8xx-dde-opcode-zero-20261017.md)（游戏内定位在第 9 节，最小复现在第 10 节）；接手所需的分支与设备状态见 [交接](../../handoffs/a8xx-dde-opcode-zero-20261018.md)；复现程序见 [`tools/a8xx-dde/minicase`](../../../tools/a8xx-dde/minicase/README.md)。

## 摘要

- Adreno 830（Odin3）上，GoW3 与 KH3 偶发的 `CP DDE BR opcode error | opcode=0`、`CP BV opcode error | opcode=0x70970001` 和 KH3 #11，原因相同：GPU 的命令处理器（CP）从某个缓冲的一整页读到全零，不报缺页，CPU 侧内容正确。
- 出错页一律在 64 KiB GPU VA 块的第 6、7 个 4 KiB 页（下称槽 6、槽 7），且同一 64 KiB 块中位置更低的缓冲已经释放。在游戏中人为构造这种布局 9/9 出错，其它布局不出错。
- 已写出一个只用 KGSL ioctl 的最小复现程序，不需要游戏、模拟器、Mesa 或 Vulkan。它表明还需要一个条件：同一进程中 CP 读过一个映射了 KGSL 零页的稀疏缓冲（VBO）。满足这些条件时，槽 7 读到零，写入槽 7 的数据也被丢弃。
- Swan（Adreno 840，当前固件 SQE `0x01510103`）上同一程序的结果与 Odin3 完全相同。
- 规避：只读缓冲用 64 KiB 对齐的 VA，GoW3 0/12、KH3 0/8 出错（对照分别为 1/6、5/6）。另一个可能的规避（稀疏缓冲不映射零页）尚未在游戏中验证。
- 根因在 SMMU、固件还是 KGSL，需要高通判断。

## 1. 现象

| 项目 | 内容 |
|---|---|
| 设备 | Odin3（AYN，Adreno 830，gen8_0）；游戏内问题均在这台上定位。Swan 上 09-28～29 的血源也出现过同签名故障 |
| 游戏 | GoW3（CUSA01740）、KH3（CUSA15072） |
| 故障签名 | `CP DDE BR opcode error \| opcode=0x00000000`；`CP BV opcode error \| opcode=0x70970001`；KH3 #11（片头保护写，CP 从命令流缓冲某页起读到全零） |
| 后果 | GPU 故障后 DeviceLost，游戏退出 |
| 自然复现率 | GoW3 冥界存档点读档后 180 s 内约 1/4～1/6 轮 |
| 读到零的路径 | DDE 取 draw-state 组、BV 取 IB1、BR 取 IB2 都出现过 |
| 零的性质 | 整页为零（KH3 中连续 145–393 个 dword）；没有缺页记录；有一次 BR 轮询同一地址约 10 s 都读到零；CPU 侧快照中该页内容正确 |

## 2. 游戏内定位

**统计**：已定位的历史零读（GoW3 14 次、KH3 4 次、10-19 自然复现 1 次）全部在槽 6/7，而只读缓冲的起始地址落在这个位置的比例只有 3–13%。KH3 的 4 次中，出错缓冲同一 64 KiB 块里位置更低的缓冲都在故障前 0.03–4.7 s 被释放，KGSL 释放时已做过 TLB 失效。

**人为构造布局**（Turnip 诊断开关 `TU_CS_HAZARD=<槽位>[:keep]`，GoW3，读档后 180 s 窗口）：

| 实际布局 | 结果 |
|---|---|
| 缓冲在槽 6，同块低位已释放 | 9/9 出错，读档后 1–75 s，多数在 25 s 内 |
| 缓冲在槽 6，下方缓冲保留 | 0/3 |
| 缓冲在槽 14，下方已释放 | 0/4 |
| 缓冲在槽 3，下方已释放 | 0/3 |
| 不放置 | 0/4 |

BV 签名 `0x70970001` 也由同一布局触发。

**64 KiB 对齐规避**（只读缓冲从 64 KiB 块起点开始，槽 6/7 只会是同一缓冲的内部页）：

| 游戏 | 对照 | 64 KiB 对齐 |
|---|---|---|
| GoW3（`csalign64k`） | 1/6 | 0/12 |
| KH3（`csalign64k`） | 5/6 | 0/8 |

GoW3 这一批对照复现率低，单独看不足以下结论；与 KH3 和布局实验合起来方向一致。`roalign64k`（命令流与 pipeline 子分配块一起对齐）还没有在游戏中单独测。

## 3. 最小复现

### 3.1 程序

`kgsl_slot_repro` 是静态链接的 Android 程序，直接打开 `/dev/kgsl-3d0` 发 KGSL ioctl，自己生成 PM4 命令。每次试验：

1. 在一个新的 64 KiB VA 块里，先分配一个 4 KiB 探测对象得到下一个 VA，再用垫片把目标缓冲 T（64 KiB，GPU 只读，写合并，内容为合法 PM4）的第一页放到指定槽位；
2. T 分配后立即释放探测对象与垫片，形成“同块低位已释放”；
3. T 存活 3 s，期间持续提交读 T 的命令。默认用 `CP_MEM_TO_MEM` 读 T 每个 64 字节行的前两个 dword，主机逐个比对。这种读法读到零时不会让 GPU 出故障，便于反复实验。

可选条件：零页映射的稀疏缓冲（VBO）及 CP 读它、VBO 绑定/解绑、并发分配释放、TLB 压力、第二个进程高优先级提交、写入核对（`--t-rw`）等，都可单独开关。

### 3.2 必要条件

| 条件 | 结论 |
|---|---|
| 只有 CP 读 T，加并发分配释放、TLB 压力、跨进程高优先级提交 | 数百万次提交都不复现 |
| 加上 2 GiB 零页映射的 VBO，且每次提交里 CP 读它 | 复现：槽 7 整页读到零，槽 6 正确；改用 IB1 读法时变成 GPU hang，SQE 停在与游戏相同的全零包头陷阱（`$19=0xbad4`） |
| 去掉第二个进程、TLB 压力、VBO 绑定活动、并发分配释放 | 仍复现（并发分配释放能加快出现） |
| 保留 VBO 但 CP 不读它 | 不复现 |
| VBO 绑满普通页，CP 读落在普通页上 | 不复现 |
| 每次提交只读 VBO 1 次；VBO 只有 64 MiB | 仍复现 |

最小条件：T 跨过槽 6→7（或从槽 7 开始）、同块低位刚释放；同一进程中 CP 读过零页映射 VBO 的未绑定部分；CP 读 T。

### 3.3 布局对照（快速配置，每组 60 s，读到零即停）

快速配置：`--mode m2m --churn-us 0 --vbo 2048 --vbo-bind-us 200 --vbo-reads 64 --life-ms 3000`。

| 组 | Odin3（Adreno 830） | Swan（Adreno 840） |
|---|---|---|
| T 在槽 6（3 轮） | 3/3，都在第 1 个 T | 3/3，都在第 1 个 T |
| T 在槽 7 | 第 1 个 T，零在槽 7 | 第 1 个 T，零在槽 7 |
| 槽 0–5、8–15（共 14 组） | 都没有 | 都没有 |
| 下方垫片保留 | 没有 | 没有 |
| 槽 0–4 保留、只释放槽 5 | 没有 | 没有 |
| 64 KiB 对齐 | 没有 | 没有 |
| 不放置（按 KGSL 自然分配） | 没有（前 3 个 T 落在槽 4、11、12） | 第 3 个 T 恰好自然落在槽 6，槽 7 读到零 |
| 槽 6 布局，只从槽 7 开始读（槽 6 已映射、不读） | 没有 | 没有 |
| VBO 读落在普通页 | 没有 | 没有 |
| 64 MiB 零页 VBO | 第 2 个 T | 第 1 个 T |
| 每次提交读 VBO 1 次 | 第 1 个 T | 第 1 个 T |

读到零的永远是 64 KiB 块的槽 7。

### 3.4 写入核对（`--t-rw`，槽 6，持续 60 s）

每次提交在读之后往槽 6、槽 7 各写一个标记，退休后主机核对：

| 设备 | 读到零的 T | 读到零的提交 | 槽 7 写丢失 | 槽 6 |
|---|---|---|---|---|
| Odin3 | 18/20 | 2829 | 2151 次，每次都与同一提交的零读同时 | 读写都正确 |
| Swan | 20/20 | 351 | 184 次 | 读写都正确 |

“读返回 0、写被丢弃、不报错”正是 KGSL 零页的表现：它的物理地址写在 SMMU 的 PRR 寄存器里，VBO 未绑定的地址都映射到它。这与“槽 7 的地址翻译落到了 KGSL 零页上”一致，但没有直接看到翻译结果。

## 4. 测试环境与驱动

| 项目 | Odin3 | Swan |
|---|---|---|
| 平台 | sun，gen8_0，Adreno 830 | canoe，gen8_2，Adreno 840 v2 |
| ROM | — | `20260922015006`（user/test-keys） |
| SQE 固件 | `0x01500081`（sha `9c8f009b…`） | `0x01510103`（sha `1f1c7bae…`） |
| GMU 固件 | — | `gen80200_gmu.bin`（sha `13c46730…`） |
| SMMU `qcom,actlr` | `0x32B`（含 PRR 使能、“+15 deep PF”） | `0x32B` |
| 系统 Vulkan 驱动 | — | 高通 `V@0855.0.9`（2026-08-20 构建） |
| 复现程序运行身份 | adb shell 用户 | root（该设备 adbd 即为 root） |
| 同时运行的其它 GPU 负载 | 已停掉 Steam 客户端（xrgamenative） | Steam 客户端在前台，GPU 70% 以上忙 |

复现程序用的二进制两台相同（sha `21b21eeb…`）。

**驱动覆盖范围**：复现程序不加载任何用户态驱动（静态链接，无动态段），既不经过 Turnip，也不经过高通的 Vulkan 驱动 `vulkan.adreno.so`；用到的是设备原装的高通内核驱动（KGSL）、GMU 与 SQE 固件。因此已经确认的是高通内核驱动加固件在这种布局与访问下的行为；高通 Vulkan 驱动在正常使用时是否会形成这种布局与访问，还没有测试。KGSL 的 `kgsl_mem_alloc` trace 事件会输出每次分配的地址、大小、进程号和 flags（第 34 位为 VBO，第 35 位为不映射零页），可用来检查它的稀疏缓冲实现和分配对齐。

**固件**：之前记录 Swan 的同类 DDE 故障已由固件更新修复；但 Swan 当前固件 `0x01510103` 上最小复现照样出现，09-28～29 Swan 的 DDE 故障快照也已是这个版本。所以那次修复没有覆盖这个机制，或者修复在别的版本中。Swan 在游戏中是否仍会出现，取决于实际负载是否形成这种布局与访问，没有在游戏中验证。

## 5. 规避方案

| 方案 | 做法 | 证据 | 代价 |
|---|---|---|---|
| 只读缓冲 64 KiB 对齐 | Turnip `TU_DEBUG=csalign64k`（命令流缓冲）/ `roalign64k`（所有只读分配） | GoW3 0/12、KH3 0/8；最小复现中 64 KiB 对齐不出现 | VA 用量增加；默认关闭，尚未在 GoW3 上测 `roalign64k` |
| 稀疏缓冲不映射零页 | 申请 VBO 时加 `KGSL_MEMFLAGS_VBO_NO_MAP_ZERO`，或保证 CP 不读未绑定区 | 只有最小复现的间接证据（CP 不读零页则不出现） | 改变 sparse residency 语义（未绑定处不再读出 0）；未在游戏中验证 |

已试过无效的方向：`cmd_no_preempt`、`cs_recycle`、mesa `c88b6ebd383`、`cs_dsb`、`dde_touch`。已排除：CPU 写缓冲未排空、SMMU 缺页、故障前页表被改写、HTW LLC。

## 6. 尚未确认或未测试

- 机理：可疑点是 GPU SMMU 的深预取（`0x32B`）、部分解除映射后 64 KiB 组内的翻译，以及与 PRR 零页的关系；也可能在 KGSL 解除映射流程中。为什么只在块的前半（槽 6/7）而不在后半出现，没有解释。
- 着色器的读（顶点、常量、纹理）在这种布局下是否也会读到零；若会，表现是不报错的画面错误。
- 高通 Vulkan 驱动下的行为（见第 4 节）。
- 最小复现中 IB2 与 draw-state（DDE）读法的对照；IB1 读法只在一轮中确认会变成 GPU hang。
- 第一批测试时，同机后台 Steam 客户端的 GPU 进程出过 3 次 GPU 故障（含同签名）；停掉它之后 30 轮没有任何故障。是否与复现程序有关，未确定。

## 7. 下一步建议

1. 把最小复现程序和本报告交给高通，注明 Odin3（SQE `0x01500081`）与 Swan（SQE `0x01510103`）都复现。
2. 在 GoW3 上跑 `roalign64k` 对照；无故障则在 A8XX 上默认开启，推送 Turnip 分支并推进父仓引用（改驱动默认行为，需确认）。
3. 评估“稀疏缓冲不映射零页”对 sparse residency 语义的影响，再在游戏中 A/B。
4. 补充：着色器读是否受影响；高通 Vulkan 驱动下的稀疏缓冲与分配对齐。

## 8. 复现方法

```bash
tools/a8xx-dde/minicase/build.sh
```

```bash
ANDROID_SERIAL=PB3110PGL6240001G tools/a8xx-dde/minicase/run_device.sh sw-demo --mode m2m --churn-us 0 --vbo 2048 --vbo-bind-us 200 --vbo-reads 64 --life-ms 3000 --slot 6 --seconds 60
```

```bash
tools/a8xx-dde/minicase/batch_controls.sh demo
```

- `build.sh` 需要 NDK 与 `references/mesa-turnip` 中的 `msm_kgsl.h`。
- `run_device.sh` 推送程序并运行一轮，KGSL 故障计数变化时收集 dmesg 与快照（需要 root）。程序也可直接在设备上运行，不需要 root。
- `batch_controls.sh` 按快速配置依次跑槽 0–15 与各对照（27 组约 30 分钟），运行前先关闭设备上其它 GPU 应用。
- 退出码：0 无错误；2 本进程上下文出故障；3 读到错误数据或写丢失；4 提交 20 s 未退休；1 参数或环境错误。
