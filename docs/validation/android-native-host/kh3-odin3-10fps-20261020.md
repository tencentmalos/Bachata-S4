# KH3 Odin3 奥林匹斯燃烧街道只有 10 FPS：分析与优化（2026-10-20）

提交：`259f85830`（HLE 去锁）、`bfbb03d8c`（音频停滞重开，Foundation `80d25c5f`，本地分支未推送）、`3e59b109d`（streaming submit 逐游戏选项）、`355a1af4f`（stream 拷贝复用）。

设备 Odin3 `6edb0593`，APK `48fa5327`（本地未提交树，含 10-19 的 stream_submit 100 与 roalign64k），
PID 22956，CUSA15072，奥林匹斯燃烧的街道、人物站立。证据 `build/validation/kh3-perf-20261020/`
（`cap1/`：Litep PROF + KGSL/sched 同窗 12 s；`perf/`：simpleperf 报告）。

## 现象

- 10.3–11.4 FPS，每帧约 6,870 个 draw、约 10 次 guest 提交、27 次宿主提交。
- GPU 不是瓶颈：`GPU.GuestFrame` 约 38 ms/帧，KGSL busy 45%，频率停在 660 MHz。
- stream_submit 运行时 A/B 无影响：0 → 11.9/11.3 FPS，100 → 10.9/11.0 FPS（之后恢复为 100）。
- 设备处于热限频：Thermal Status 2，CPU 频率上限被压到 2.75 GHz（policy0，原 3.53）和 3.07 GHz
  （policy6，原 4.32），采样期间大核平均 2.31 GHz。
- 本局没有加载 `kh3_cpu_waits` guest patch；本局开头因驱动 UUID 变化清掉了 2,301 个旧管线缓存，
  前期有编译卡顿，与稳态 10 FPS 无关。

## 一帧的时间去哪了（3 s 窗口，30 个完整帧，平均 93.7 ms）

- **GpuComm**：on-CPU 61%（1,838 ms/3 s），`Rasterizer.Draw` 8.0 µs/draw，约 57 ms/帧；其余约
  36 ms/帧在睡眠，唤醒它的是 guest 提交线程（Guest-31/44/57），即在等 guest 生成命令。
- **UE4 RHI 并行翻译线程**（Guest-5..9 与 Guest-44）：3 s 内 sceGnmDrawIndex HLE 188k + 27k 次
  （每帧约 7,500 次）。85% 在 8 µs 内完成，但 28% 要 16 µs–1 ms，慢的这部分占全部 DrawIndex 时间的
  94%。每个线程每秒约 8,000 次被唤醒、一半在 20 µs 内又阻塞，约 11% 时间排队等 CPU。渲染线程
  Guest-57 79% 时间在 cond_wait 等它们。

## 根因：每次 HLE 往返都要过两把全局宿主锁

`simpleperf record -e sched:sched_switch --call-graph fp`（6 个 RHI 线程，4 s，185,504 次切出）：

| 切出位置 | 占比 |
| --- | ---: |
| `FexCpuContext::RunInternal` 的 `resume_continuation`（每次 HLE 返回 guest） | 59% |
| 　其中直接等 FEX 上下文锁 `lock_` | 77% |
| 　其中在 `lock_` 内调 `GuestAddressSpace::Query(rip)` 再等地址空间锁 | 23% |
| DrawIndex 编码器 HLE 的 pin（`AcquireDataBatch` 43% / `~PinnedSpan → ReleasePin` 56%） | 31% |

两把锁都是整个会话共用的 `std::mutex`：FEX 上下文的 `lock_` 和 `GuestAddressSpace::lock`（GateMutex，
解锁时还要 `RefreshExecutionGateLocked`）。一次 DrawIndex 至少过 4 次：建 pin、放 pin（`erase_if`
线性扫描 pin 表）、continuation 的 `lock_` 与其中的 `Query`。

同一组线程的 on-CPU 采样（`task-clock`，合计约 1.5 核）：30% 在内核 `_raw_spin_unlock_irqrestore`
（futex 唤醒/调度），17.5% 在编码器包装本身（`guest_graphics_hle.cpp` 每次把 `max(window,4096)+64`
个 dword 填成 guard 并逐个检查，至少 32 KB 内存读写），12.9% 在持锁期间的 `CheckDataRequestsLocked`
（锁内时间长，排队更严重）。

## 为什么比 10-13 慢

10-13 的已提交代码默认把 DrawIndex 系列放在 guest 叶子快路径里（不进 HLE）。10-14 查闪黑时，
本地未提交改动把默认改成 `LeafDefault = LeafAll & ~LeafDrawIndex`（rwlock 快路径与 DrawIndex 叶子
快路径同时开才闪，原因未明），当前 APK 带着这个改动，日志 `leaf_routed=3`。于是渲染线程的每个 draw
又回到 HLE，落在上面的锁上。这一点还没有用同场景重启 A/B 验证。

## 可选方向

1. 确认：以 `debug.shadps4.leaf_fastpath=all` 重启游戏回到同一位置测 FPS（会带回已知的单帧闪黑）。
2. 保留 DrawIndex 在 HLE、去掉热路径上的全局锁（对所有 HLE 密集的游戏都有用）：
   - 编码器 guard 只填/查 `window` 之后的 64 个 dword；
   - `resume_continuation` 在没有排空/映射变化时跳过 `lock_` 与 `Query`（按代际号判断）；
   - 短时 HLE pin 改为不经全局 mutex（例如按线程计数、排空时再汇总），`CheckDataRequestsLocked`
     的映射查找移出锁或缓存命中。
3. GpuComm 自身 8 µs/draw（GoW3 为 4.7 µs）与热限频是另外两项，即使 guest 侧不再排队，GpuComm
   也会把这里限制在约 17 FPS。

## 优化：HLE 热路径去掉全局锁（10-20 上午）

### 改动

1. **编码器 guard**（`guest_graphics_hle.cpp`）：只填、只查 `window` 之后的 64 个 dword。缓冲区容量不变
   （至少 4096+64 dword），`window` 之外的内容本来就不写回。原来每次调用都要写满并逐个检查
   `max(window,4096)+64` 个 dword（每次至少 32 KB 读写），每帧约 7,500 次。
2. **HLE 返回不拿 `lock_`**（`fex_context.cpp` 的 `fast_continuation`）：owner 依次发布 `entering`、
   用 `TryAcquireExecutionLeaseFast` 拿 lease（执行门关着就不拿锁、直接退回）、发布 `running`，最后才读
   `pending_hint`、owner callback 计数和 `debug_attached_`。控制方反过来：`RequestInterruptLocked`
   先发布 `pending_hint` 再读 `running`，`QueueOwnerCallback` 先加计数再读 `running`，排空在
   `BeginDrain` 关门之后把 `entering` 也当作运行中，并等 `running`、`entering` 都清零（全部 seq_cst）。
   所以要么控制方看到 owner 在跑（照常布置 poll 页或等待），要么 owner 看到请求后在 `lock_` 下按 HLE
   边界的规则退回（必要时恢复 poll 页、`running=false`、通知）。执行区检查按 mapping/code generation
   缓存（`continuation_executable`），慢路径也用它，命中时不再在 `lock_` 内调 `space_.Query`。
   `running` 只在持有 lease 时为真；所有会调 `DiscardTranslations` 的路径都要求 lease 数为 0，进 JIT
   必须持 lease，因此不受影响。快路径不清 `stopped_snapshot`，`Threads()` 对运行中的线程改报空快照
   （其他读者本来就先看 `running`）。
3. **短 pin 不经全局 mutex**（`address_space.cpp`）：锁内路径校验成功后记下所在映射（线程局部，按
   space 实例和 mapping generation 失效）；之后同一映射内的单区间 pin 走 `TryAcquireFastPin`：占一个
   slot、发布、再读数据门和 generation，变了就释放退回锁内路径。所有需要看到全部 pin 的地方（Unmap、
   Protect、MapFreshData/ProtectData、UpdateDataMapping、PrepareDataMapping、FinishDrain、Quiesce、
   UpdateVmUnderToken、准入时的 own-pin 判断、Counts）先关数据门再扫 slot；数据门在 quiescence、sink、
   任何 data edit 存在时关闭，并在每次解锁时重算。释放时若有等待者再拿锁通知。

开关（会话启动时读取，默认开）：`debug.shadps4.fast_data_pins=0`、`debug.shadps4.fast_hle_resume=0`；
日志行 `HLE fast paths: data pins on|off, continuation on|off`。guard 精简没有开关。

## 深入分析：render scale、回读与剩余瓶颈（10-20 晚，APK `7ad26f1e`，燃烧的街道）

`gpu_memory request` 两次采样相减（窗口内的增量）与 pass 日志：

- **render scale 生效**：倍率 75%，窗口内 98.8% 的 draw 落在缩放附件上；原生 pass 只占 pass GPU 时间
  2.3%。降级原因只有启动时的少量 semantic-native/alias/mixed-pass 转换，场景中不再增加。
- **没有来回回读**：`upscaled_readbacks`、`image_buffer_syncs`、`fused_readbacks` 均为 0，场景中
  `texture_uploads` 不增长，GC 无下载。
- **GPU 频率停在 660 MHz**：GPU 每帧约 34–38 ms，忙 80–83%。msm-adreno-tz 在这个忙度下不升频
  （下限 660、上限 1100）；GPU 忙度不到 85% 是因为它在等 GpuComm，不是 GPU 本身受限。
- **GpuComm 占满一个核**（约 10.9 s/10 s，约 48 ms CPU/帧），是关键路径。其中 stream 拷贝每帧约
  88.8 MB，79.9 MB 与同一帧内上一次拷贝的内容相同；`memcpy` 占 GpuComm 13.4%。
- **pass 碎片**：每帧约 315 个 pass，262 个只有一个 draw；采样已绑定附件造成约 126 次重开；
  G-buffer pass（7 个颜色附件 + D32S8）约 13 ms，占 pass GPU 时间 25 ms 的一半。
- **streaming submit 对 KH3 是必需的**：同一会话 `stream_submit 0/100` 交替两轮，12.2/12.0 →
  22.7/22.6 FPS，GPU 每帧时间 39 → 34 ms（提交拆分没有增加 GPU 时间）。关掉时 GPU 要等 GpuComm
  录完整帧才开始，两者串行（约 44 + 39 ms）；打开后帧内重叠，帧长接近 GpuComm 一侧。

## 架构评估：为什么提前提交只是权宜之计

提前提交解决的是“GPU 等 GpuComm 录完整帧”，做法是按 draw 数切块：切点与游戏的数据依赖无关，
效果因游戏而异，flush 还会切断 render pass（`resumed: flush` 计数），所以只能逐游戏开关。真正的约束是
GpuComm 单线程每 draw 工作量太大、且帧内的提交时机只由 PM4 边界决定。参考两种更彻底的设计：

- **bbport（血源 PC 版）两阶段流水线**：前段解码 PM4、做寄存器 diff 与管线选择，后段做资源绑定与录制；
  包只带上一包之后写过的寄存器块和 user data 快照，有序任务（EOP/WRITE_DATA/flip）交给后段，
  `WAIT_REG_MEM` 遇到已交给后段的 fence 视为满足；另有常量 ring 与各类 memo 缓存。
- **Azahar `gpu_async`**：解码成 job，单一 GPU 执行线程；每个 job 带精确的读写地址范围，按范围求依赖、
  合并失效；完成通过 completion queue/mailbox 回到 guest 侧，guest 等待可恢复调度；寄存器按脏组更新，
  uniform 走 patch + 只追加 arena，不整块复制。

对照 KH3 现状，建议的顺序：

1. **同一同步窗口内 stream 拷贝去重**（不做哈希）：参考 Azahar 的只追加 arena 与 bbport 常量 ring，
   在 CPU 没有写过、也没有越过 fence 的窗口内复用上一次的拷贝；目标是那 79.9 MB/帧冗余拷贝。
2. **脏寄存器组 / 管线 key 复用**：按 Azahar 的脏组和 bbport 的 memo，减少每 draw 的状态比较与
   特化查找（GCN v2 阶段 C 的剩余工作）。
3. **按依赖提交，取代按 draw 数切块**：提交点由“消费者需要”决定（guest 等待的 label/查询、回读、跨队列
   依赖），用精确访问范围判断，而不是每 100 个 draw；做到后 streaming submit 可以退役。
4. **阶段 B（两段流水线）**：KH3/Odin3 现在大体满足 GCN v2 spec 的启动条件（GpuComm 占满帧、GPU 忙
   < 85%），但设备在 Thermal Status 3–5、且没有 LiteP 同窗采集的逐帧相关系数，按 spec 还不能启动；
   先做 1–2 降低每 draw 工作量。

## 同一窗口内复用 stream 拷贝（10-20 晚）

GpuComm 每帧把约 90 MB 小只读缓冲拷进 stream buffer，其中约 80 MB 是同一帧里已经拷过的同一范围
（UE4 每个 draw 都绑 View/Frame 等 uniform buffer）。现在同一 (地址, 大小) 在同一个“窗口”内再次只读绑定时，
直接绑到上一次的拷贝，不做哈希、不比内容。实现在 `video_core/buffer_cache/stream_reuse.h`，
`BufferCache::ObtainBuffer` 的 stream 路径里查表（2048 项直接映射，按 (地址, 大小) 精确匹配）。

窗口三个条件同时不变才复用：

- **同一个 scheduler tick（命令缓冲）**：stream buffer 只在写入它的 tick 在 GPU 上完成后才回收该区域，
  跨 tick 绑旧拷贝会读到被覆盖的数据。ring 回绕时会先提交当前 tick，所以回绕后也一定换窗口。
- **命令处理器没有经过会写或等待 guest 内存、或让 guest 与其他队列运行的事件**：除寄存器写、draw、
  dispatch、标记、缓存维护、不写内存的 EVENT_WRITE 之外的所有包（WAIT_REG_MEM、WRITE_DATA、DMA_DATA、
  EOP/EOS/RELEASE_MEM、CE 计数与 dump、未知包等），以及队列 yield、新提交、宿主命令、flip、遮挡计数 dump。
  白名单之外一律结束窗口。
- **`MemoryManager::GuestViewEpoch()` 不变**：所有宿主写 guest 内存（`TryWriteBacking`、
  `WriteBackingUnchanged`、`CopyGuestRegions`）、HLE 报告的 guest 写（`InvalidateMemory`）和每次映射写锁
  释放（map/unmap/commit/decommit）都会推进它；查表前先 `WaitPendingWritebacks`，再读 epoch。

GPU 写过的范围本来就不走 stream 路径（先判断 `IsRegionGpuModified`）。不检测的只有普通 guest CPU 写：
游戏在 GPU 还没读之前改写缓冲、中间没有 label、等待或新提交，在主机上本身就是与 GPU 的竞争。

- 开关：默认开；`upload_diag stream_reuse on|off`（无参数时打印窗口统计），
  `debug.shadps4.stream_reuse=0|1`，`SHADPS4_STREAM_REUSE`。`gpu_memory status` 增加
  `stream_reuse enabled= reused= bytes= misses empty/tick/window/memory=`，`upload_diag status` 增加窗口数、
  按原因的结束次数和结束窗口最多的包。

## 寄存器脏位图与渲染目标 memo（GCN v2 阶段 C 第一项，10-20 晚，已提交）

先存档了 Azahar / bbport 的调研（[gpu-async-research-20261020.md](../../gpu-async-research-20261020.md)）。bbport 没有
“按值比较”的脏位图：`RegDirty` 只按 32 字块记“写过”，用于把寄存器增量交给阶段 B；省重算靠以原始寄存器字节和代际为键的
memo（render target 查找、BeginRendering 签名、上次的排列、纹理集合）。Azahar 只在值变化时标脏组。这里取 Azahar 的脏组
做法，消费者照 bbport 的 memo 写法。

**剖析（stream 拷贝复用之后，KH3 燃烧的街道，GpuComm 占满一个核）**：`BindResources` 25.8%（`ObtainBuffer` 11.6%）、
`GetProgram` 15.3%（其中 SRT 走表 `RefreshFlatBuf` 6.7%，依赖 guest 内存）、`BeginRendering` 10.2%、`BindVertexBuffers`
8.5%、`PrepareRenderState` 6.2%、`UpdateDynamicState` 1.8%、`BuildRuntimeInfo` 0.55%。只依赖寄存器、能靠脏位跳过的主要是
渲染目标（`PrepareRenderState` + `BeginRendering`，约 16%）；`GetProgram` 的输入还包括 guest 内存里的 sharp，不能只看寄存器。

**实现**：

- `amdgpu/reg_tracker.h`：`RegTracker::Write` 把 SET_CONTEXT/SH/UCONFIG/CONFIG_REG 写进寄存器文件时逐字比较，只有值变化才推进
  所属组的代际；`ClearState` 与回放恢复寄存器时 `InvalidateAll`。组表由 `Regs` 的字段偏移生成；目前一个组 `Targets`：颜色/深度
  缓冲（含清除值）、两个颜色掩码、颜色/深度控制、深度渲染控制/override、HTILE 基址，以及无附件时用的三个 scissor 与 window
  offset。draw 包直接赋值的寄存器（index 基址、数量、draw initiator）不在任何组。
- 渲染目标 memo（`PrepareRenderState`）：`Targets` 代际、两组尺寸提示、管线的 MRT 掩码、未用小深度标志与纹理缓存的
  `ImageSetGeneration` 都不变时，沿用上一个 draw 找到的 image 与描述，只做 `FindImage` 的使用记账
  （`TouchFoundImage`：用途、最近访问 tick、LRU；同一命令缓冲内只做一次）。
- render state memo（`BeginRendering`）：scheduler 仍以上次的 RenderState 开着 pass（屏障、拷贝、上传、提交都会结束它），
  `Targets` / image 集合 / `ContentGeneration` / 新增的 `MetaClearGeneration`（CMASK/HTILE 被标为已清除时推进）不变，
  本 draw 的目标、采样数、被采样的目标相同且目标的 `state_version`（布局变化与 backing 更换）未变时，直接沿用上次的 state，
  只补 pass 访问登记和用途标记。带清除的 state 不复用（下一个 draw 会改为 load）。
- 顺带：`HostMarkersEnabled()` 与标记函数改用构造时缓存的设置（`EmulatorSettings` 每次使用都取全局锁并复制 shared_ptr，
  每个 draw 调用多次，约 1.6%）；`FetchShaderCache` 由 4 项扩到 16 项（UE4 的 VS 配合的顶点布局多于 4 种，原来每个 draw 都
  重新解析 fetch shader，约 1.8%）。
- 开关：默认开；`upload_diag target_memo on|off|verify`，`debug.shadps4.target_memo=0|1|2`。verify 对每次命中照常走完整路径，
  比较 image、视图与 RenderState，不一致计数并记日志。

**测试**：`tests/common/reg_tracker_tests.cpp`（NDK 编译在 Odin3 上运行）100029 项 0 失败：组表覆盖、同值不推进、组外寄存器不推进、

## SRT 走表降本与管线 key 增量维护（10-20 夜，已提交）

### SRT 门控：测过，不做

设想是 SRT 走表在 (permutation, user data) 与读到的 guest 内存都没变时跳过。先加了默认关的诊断
`srt_gate on|off|status|reset`（`shader_recompiler/srt_gate_diag.*`），记录每次走表的输入与读到的字节。KH3 燃烧的街道
228.6 万次走表（证据 `build/validation/stagec-20261020/srtgate1`）：

- 与上一次走表输入完全相同的只有 2.3%；(permutation, user data) 以前出现过的 27.6%。
- 后者中 46% 读到的表内容已经不同：UE4 LCUE 在同一地址反复重写描述符表。要安全跳过，还得对读到的范围做写跟踪；
  可省的上限约为走表开销（GpuComm 的 6–7%）的 15%，即 1% 左右。

所以改为让走表本身便宜。

### 改动

- **SRT 预编译计划**（`ir/passes/srt_portable.h`）：`PortableSrt::Prepare()` 在生成或从缓存读出程序时，把命令编译成步骤：
  常量入栈、表达式入栈、出栈、连续常量拷贝合并成的一段、表达式拷贝。`Run()` 按步骤执行；合并规则、读的次数与顺序都与解释
  执行相同（单段最多 64 dword，偏移须按 32 位不回绕地连续）。只有常量偏移的计划不用表达式 memo；有表达式的计划用栈上 128 项
  memo（表达式更多时用堆），不再访问 `thread_local`。DebugBus `srt_plan plan|interpret|verify|status`；verify 对每次走表在副本
  上跑计划、在真缓冲上解释执行并逐字比较。
- **内存锁的持有统计默认关**：`MemoryManager::mutex` 每次加共享锁都更新线程局部的持有槽；宿主 DSO 由 dlopen 加载，每次访问
  `thread_local` 都要经过 `tlsdesc_resolver_dynamic`。现由 `SharedFirstMutex::SetHoldTracking` 控制（`memory_lock holds on|off`，
  默认关），切换时推进期号，旧期号的槽不再计入。
- **管线 key 增量维护**（`vk_pipeline_cache.cpp`）：
  - 新增寄存器组 `KeyState`（`reg_tracker.h`）：裁剪、多边形、图元类型、阶段使能、LS/HS 配置、导出格式、混合、视口与深度范围、
    GS 模式、stream-out。`RefreshGraphicsKey` 的第一遍（阶段之前）只读 `Targets` 与 `KeyState` 的寄存器、未用小深度策略和设备常量，
    两组代际与策略都不变时直接拷贝上次的结果；第二遍（阶段之后）还取决于片元着色器的 MRT 掩码，掩码也相同时拷贝上次的输出。
  - `GetGraphicsPipeline`：key 与上一个 draw 完全相同时跳过哈希与查表，直接用上次的管线（仍做 `PromoteIfPending`）；删除管线时
    清掉该指针。
  - 开关 `upload_diag key_memo on|off|verify`、`debug.shadps4.key_memo=0|1|2`，默认开。verify 对命中照常重算，比较两遍的结果与
    查到的管线。
- **fetch shader 缓存**：原先每个 Program 一个 16 项环，KH3 场景中仍有大量解析。先改为 PipelineCache 一份、按代码地址直接映射的
  1024 项表，无效（`FetchShaderCache::Find` 2.42% → 2.39%，`ParseFetchShader` 1.61% → 1.60%），说明是冲突未命中；再改为
  1024 组 × 4 路、LRU，并加计数（`upload_diag key_memo` 输出 `fetch_shader_cache hits/misses_new/misses_changed`）。
- 新加的计数只由 GPU 命令线程写，用 relaxed load + store 而不是原子加（Android 的 ARMv8.0 构建里原子加是一次外部函数调用）。

## sampler 前置缓存与宿主 DSO 去 PLT（10-20 夜，已提交）

上一节之后 GpuComm 剖析里还剩两个不涉及模拟语义的固定开销：`TextureCache::GetSampler` 每个纹理每个 draw 算一次
XXH3 并拿一次 `samplers_mutex`（约 1.1%），以及宿主 DSO 内部调用都经 PLT（`@plt` 自身 4.1%，最大的调用方就是
`GetSampler`）。

### 改动

- **`TextureCache::GetCommandSampler`**（只给 GPU 命令线程的 `BindTextures` 用；XR presenter 仍走带锁的 `GetSampler`）：
  按 S# 原始 16 字节与 `is_depth` 直接映射的 256 项表，命中时不算哈希、不拿锁。条目记下写入时的 `gc_tick` 与
  `sampler_generation`：每个 GC tick 内第一次使用仍走 `GetSampler`，sampler 的 LRU tick 与原先相同；GC 释放任何 sampler
  时（同在 GPU 命令线程，`samplers_mutex` 内）推进 `sampler_generation`，所有条目失效。键与原表一致（不含 border color
  基址），所以命中返回的就是原表会返回的 sampler。开关 `upload_diag sampler_memo on|off|verify`、
  `debug.shadps4.sampler_memo=0|1|2`，默认开；verify 对命中照常走带锁查找并比较。
- **宿主 DSO 加 `-Wl,-Bsymbolic-functions`**（`CMakeLists.txt` 的 `shadps4_host`）：宿主导出约 6.5 万个符号，内部调用自己定义的
  函数原先全部经 PLT。加上后 `R_AARCH64_JUMP_SLOT` 23800 → 736（只剩 libc、libc++、驱动等外部库），导出符号数不变
  （65222）。与其他 app DSO 重复定义的只有 nlohmann::json、libc++、tsl 的模板实例和少量内联函数（`libshadps4_fex_session.so`
  109 个、`libbachata_pkg.so` 的 tiny-AES 10 个），代码相同；宿主不定义 `operator new`、`malloc` 之类需要被插入覆盖的函数，
  数据引用仍按全局解析。只影响 Android 宿主 DSO，桌面不变。
