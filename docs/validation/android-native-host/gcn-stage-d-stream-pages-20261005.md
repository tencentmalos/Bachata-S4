## 1. 结论

| 项 | 状态 |
|---|---|
| 做法（最终 v3.1） | 连续三个写周期都以 CPU 写结束、且上一周期被绑定不超过 4 次的页（流式页）不再写保护，保持 CPU 脏；每次上传覆盖它时哈希内容，与上次复制时的哈希比较，变了才复制。GPU 看到的是绑定时 Guest 内存的内容，与写跟踪一致（§2） |
| 放弃的做法 | “每代复制一次”：回放压力测试中出现过期副本，帧不同；“每次绑定都比较、不限绑定次数”（v2）：哈希占 GpuComm 27–30%，净亏（§4） |
| 正确性 | 单元测试 726 项 0 失败（含 20 万步随机读写），负对照分别失败 40 项与 2 项；外置显卡回放：关、开（门槛 1 周期，57 页晋升）均与基线逐帧、逐事件全同，共 6 次（§3、§4） |
| 性能（外置显卡） | 写缺页每帧 44–51 → 12–24 次（约 −70%），预测放行页 1000+ → 90–320；GpuComm 上写保护与复制共少约 5 个百分点，哈希多约 9–11 个百分点，`ObtainBuffer` 合计多约 5.5 个百分点。**桌面上基本抵消，没有净收益**，默认保持关闭（§4） |
| 回放工具 | 回放改为只对仍被写保护的页模拟写缺页（原来对所有增量页一律失效），回放因此会走写预测与流式页；外置显卡与核显上关流式页的回放均与基线全同 |
| 开关 | DebugBus `upload_diag watch_stream on|off [1|2|3]`（`status` 显示 checked/copied/promoted/demoted/busy），环境变量 `SHADPS4_WATCH_STREAM=1`、`SHADPS4_WATCH_STREAM_CYCLES=1..3`；回放摘要在开启时多一行 `stream_pages ...` |
| 另发现 | 外置显卡上回放偶发 G-buffer 单个 MRT 一帧不同（今天约 40 次中 3 次），核显上 13 次未出现；与流式页无关（§5） |

## 2. 设计（v3.1）

**晋升**（`RegionManager::CleanForUpload`）：每页一个 2 位计数，记连续以 CPU 写结束（写缺页或写预测提前放行）的写周期数，某个周期没有 CPU 写就清零。满足以下全部条件时晋升：计数到 3（`stream_promote_cycles`，可设 1–3）；页不是 GPU 修改的；上传来自 16–64 KiB 的只读绑定（≤16 KiB 的只读绑定走 stream buffer，不经过写跟踪）；该页上一周期被绑定不超过 4 次（`StreamMaxBinds`）。晋升的页这次照常复制，之后不再写保护，保持 CPU 脏。

**每次上传**（`ForEachPendingUpload` 在区域锁内先于 `CleanForUpload`）：

- 范围内的流式页逐页哈希（`hash_pages`，XXH3），与该页上次复制时的哈希比较，记下变了的页；要复制的页数（staging 预留）因此与随后实际复制的完全一致。
- `CleanForUpload` 复制普通脏页、新晋升的页和变了的流式页，复制完成后才提交新哈希（复制若中途失败，下次仍会再比、再复制）；新晋升的页在复制之前哈希，两者之间的写由下一次比较发现。
- 每页记录自上次复制以来的绑定次数（流式页开启时计数），用于晋升条件与降级。哈希与计数放在区域的 `ContentHashes`（与写预测共用，按需在锁外分配；某页第一次以 CPU 写结束周期时申请）。

**降级**（重新写保护；降级的页仍是 CPU 脏，下一次上传按普通页复制并写保护）：

- GPU 写的绑定：上传前降级范围内的流式页；
- 显式清除 CPU 脏（`ForEachModifiedRange<CPU, true>`、`UnmarkRegionAsCpuModified`）；
- 自上次复制以来被检查 256 次（`StreamDemoteChecks`）内容都没变：CPU 已经不再写它，或者它被绑定得比变化频繁得多；
- 开关关闭：下一次上传降级区域内全部流式页。

**不需要的东西**：显式标记 CPU 修改（`MarkRegionAsCpuModified`）对流式页是空操作，内容由下次比较决定；CP 自己写内存（`WRITE_DATA`、`DUMP_CONST_RAM`、fence、信号量）、Guest 在提交处理过程中写数据，都由绑定时的比较覆盖，不需要通知，也不需要“代”的划分。

**开销模型**：一次检查约 0.18 µs（实测：哈希占 GpuComm 11.2%、约 0.54 ms/帧、2962 次/帧），换掉的是每个写周期一次写缺页（Guest 线程上的异常分发加取消保护，桌面约 10 µs 量级）和一次重新写保护。写预测已经把大部分写周期变成“不缺页、只重新保护”，桌面上省下的主要是剩下的那部分写缺页。

## 3. 正确性

**单元测试** `tests/common/memory_tracker_stream_tests.cpp`（`build/run-tracker-tests.cmd`，生产 MemoryTracker/RegionManager，只替换 OS 保护与设置）：替身 Guest 内存每页记一个版本号，写被保护的页触发写缺页，写未保护的页不触发；每次上传之后，绑定范围内每一页 GPU 副本必须等于 Guest 内存。覆盖：三周期晋升、未变不复制、两次上传之间无缺页的写被下一次上传复制、部分范围、显式标记、GPU 写绑定（变与未变）、连续未变降级（仍在变的页不降级）、开关关闭、大绑定与写绑定不晋升（大绑定仍检查流式页）、每周期绑定超过 4 次不晋升、断档清零、1/2 周期、20 万步随机读写/上传/GPU 写绑定（门槛 1 周期：25116 次晋升、77283 次检查、43539 次复制、13070 次因绑定过多不晋升）。726 项 0 失败。

负对照（替换 `region_manager.h` 后重编测试）：

| 变体 | 失败 |
|---|---|
| 比较永远判为“未变” | 40 项（含随机测试读到过期副本） |
| 不排除绑定过多的页 | 2 项（正好是这两项；它是性能策略，正确性检查全过） |

## 4. 迭代过程

**先试的“每代复制一次”**（一代内每个流式页只复制一次）：

| 版本 | 代的边界 | 结果 |
|---|---|---|
| `82ed8005` | 每次 resume、每个等待包 | 核显每帧 258 代；1024 代重新验证一次即每 4 帧全部降级再晋升：开时每帧缺页 103–112 次（关 42–44 次） |
| `bc37e63f` | 提交第一次 resume、每个等待包 | 仍每帧 256 代：血源一帧约 400 个 `WAIT_REG_MEM`，多数在等早先 GPU 工作的 fence |
| `3d13481a` | 提交第一次 resume、被 Guest 内存（而非待定 fence 值）满足的等待 | 外置显卡每帧 62.5 代，全部来自提交（含计算队列）；降级与晋升各 34 页/帧 |
| `6ae10c73` | 同上，重新验证改为 16384 代 | 开时缺页 30.6 次/帧，但每帧复制 1799 页；**回放压力测试（门槛 1，75 页晋升）第 4 帧不同** |

压力测试不同的原因：回放在等待被待定 fence 值满足时也会写入录制时的增量（录制时 Guest 在 CP 处理这份提交的过程中写了数据），不开新代，本代已复制过的流式页沿用旧副本；写跟踪在绑定时复制，能看到这些写。实机 Guest 同样会在 CP 处理过程中写数据，代的快照比绑定时更早，所以改为每次绑定比较内容。

- v2 中平均每个流式页每帧被检查 13 次以上（例如每个 draw 都绑定的大常量缓冲），检查越来越多，GpuComm 线程时间 6.1 → 9.4 ms/帧。
- v3 检查次数降到约 1000 次/帧，GpuComm 持平，但每帧约 8 页来回晋升/降级（内容被每帧重写成相同值的页，16 次检查就判为不再写），每次往返多 3 次写缺页。
- v3.1 往返基本消失，写缺页减少约 70%，但留下的流式页检查次数随运行时间增加；GpuComm 多出的哈希与少掉的写保护、复制大致抵消，`ObtainBuffer` 合计多约 5.5 个百分点。线程 CPU（60 FPS 封顶，各轮 6 s）：GpuComm 开 5.59/6.40/5.68、关 5.83/5.48/5.68 ms/帧，进程开 39.5/33.1/38.0、关 33.9/32.8/35.6 ms/帧，噪声大于差别。

**结论**：桌面上写预测已经让写跟踪很便宜（每帧约 45 次写缺页、其余靠提前放行），流式页把 Guest 线程上约 0.3–0.4 ms/帧的写缺页换成 GpuComm 上约 0.3 ms/帧的哈希，没有净收益；它也不减少 `ObtainBuffer`，对阶段 D 的验收目标（`BindResources` 加 `ObtainBuffer` 降到 20% 以下）没有帮助。保留代码与开关（默认关），留待在 Android 上评估：那里写缺页约 50 µs，但 GpuComm 是瓶颈，ARM 上哈希也更贵，要实测才知道。

**回放改为按写缺页通知缓存**（`gpu_replay_player.cpp`，与流式页无关、默认生效）：回放把增量页写进 Guest 内存后，原来对整段调用 `InvalidateMemory`（一律置 CPU 脏）；现在只对仍被写保护的页调用 `InvalidateMemoryFromWriteFault`（与实机写缺页相同：记写周期、写预测提前放行），未被保护的页不通知（实机写未保护的页也不产生缺页）。回放因此会走写预测；外置显卡与核显上关流式页的回放均与基线全同。5 帧的回放里门槛 3 不会有页晋升（页大多隔帧重写），所以用门槛 1 做压力测试，晋升后的页在剩余帧中被检查 25 次，覆盖有限。

## 5. 外置显卡上的偶发回放差异

`941ba970` 门槛 3 的那次回放 0 页晋升（流式页实际未起作用），第 2 帧从事件 904 起 image 22（`0x26f090000`，960×540，G-buffer MRT2）13 行不同，随后的光照与后处理图像跟着不同。与阶段 A 记录的那次完全相同（第 2 帧 image 22），阶段 C 记录过一次第 0 帧 image 21（MRT1）。这一次是该 exe 的第三次回放，所以不只是“新编译后的第一次”。

今天外置显卡上约 40 次回放出现 3 次（约 7%），核显上 13 次一次也没有。外置显卡多走两条核显不走的路径：stream DMA（独显上的拷贝专用队列，图形提交等待 timeline）与系统内存 stream buffer。stream DMA 默认与关闭交替各回放 8 次，16 次全同，差异没有出现，所以还不能归因；按约 7% 的发生率，每组需要五六十次以上才有区分度，或者用逐 draw 哈希在出现差异的那次回放里直接定位。

## 6. 未覆盖 / 下一步

- Android 上的流式页实测（写缺页贵，但 GpuComm 是瓶颈、ARM 上哈希更贵）。
- 外置显卡回放偶发差异：长时间统计或逐 draw 定位（§5）。
- 5 帧回放覆盖有限；可以抓一段更长的 trace（30 帧）在门槛 3 下对比开关。
- 动态图像表的快照按 resume 刷新（原有行为），与“每代复制一次”有同样的隐患：Guest 在等待之后改表时会用旧快照。本轮没有改动，记为待查。
- 阶段 D 的验收目标要靠其余几项：SRT 走表按代际门控、sharp → 稳定 heap 槽、小只读常量快照复用、`ObtainBuffer` 的代际判断。
