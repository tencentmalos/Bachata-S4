## Android video startup blocker found and repaired (21:18 follow-up)

At guest caller `0x6e1b63`, GoW III requests AVC profile 100, level 42, 1920×1088 and
`maxDpbFrameCount=-1`. The game writes this sentinel explicitly at `0x6e1b27`.

the Android bridge rejected negative counts with `0x80c1000e`, causing the video
worker to exit before creating a decoder. The shell continued rendering its title

rejects `-2`, and exercises automatic sizing through real H.264 decode/reset/delete.

## Startup bridge repair (follow-up request)

The follow-up request explicitly authorizes compatibility repairs and AYN gameplay validation.
The complete import inventory above was audited before implementation. Desktop registrations
are declarations, not permission to call native code with guest pointers.

Implemented changes:

- Allocate session-owned `EntryParams` and copy argv **before** guest `_malloc_init` / `DT_INIT`.
  `getargc` returns that session's count; `getargv` returns the guest address of the null-terminated
  argv array, never the desktop `entry_params` pointer.
- Stack-check failure, `_exit`, and both debug-exception entry points stop the guest session with
  the operation/error identified, rather than using desktop host-process assertions.
- Bridge all six original Videodec imports through the desktop `VdecDecoder`: resource query,
  create, decode, flush, reset, delete. Handles are session tokens; compressed packets are padded
  copies; every output is admitted before decoding; workspace addresses never escape to FFmpeg.
  A decoded frame larger than the supplied framebuffer returns the library's size error.
- Bridge VideoOut gamma setup and color application through checked copies and the existing
  presenter. The floating-point gamma argument comes from guest XMM0.
- Extend the offline WebAPI context/request lifecycle with original CreateContext/SendRequest,
  HTTP-status queries and abort. Use the session's initial local user, matching desktop's user
  selection without dereferencing the desktop UserManager in Android. A failed offline send
  keeps its real error and does not publish an invented HTTP status.

Targeted tests on Thor: `guest_videodec_tests` **747/0**,
`guest_psvr_services_tests --webapi-only` **215/0**. These cover real H.264 decode,
cross-mapping input, rejected output without consuming the packet, oversized-frame rejection,
foreign/stale handles, request retirement, and unchanged outputs after offline failures.
The full PSVR test was also attempted: its existing Move timestamp checks failed six times;
that unrelated path is outside this change's acceptance and was not repaired.

The first full repair APK (`fd54812f…`) crashed during Prepare because the new WebAPI wiring
still read `UserManagement.GetDefaultUser()` at construction. Its native stack identified that
call. The wiring was corrected to use the already-created `GuestUser` snapshot (including the
existing Android local-user fallback), and decoder retirement was made explicit before VM teardown.
Runtime acceptance below must use the corrected APK, not this intermediate build.

### Submission deadlock and diagnostic limits

Android held `SubmissionMutex` around standalone `sceVideoOutSubmitFlip`. Another guest
thread could hold that same mutex while waiting for the GPU command queue to drain, while
the queue waited for a display label only the flip thread could release. Standalone flips
now use VideoOut's own queue locking, matching the desktop entry; the outer execution
lease still protects VM lifetime. The previous process rendered 47,919 frames and then
completed a normal UI Stop. This proves the deadlock is past, not gameplay acceptance.

Black-screen trace: 233 actions / 22 submits; last draw FS `0x4aec30af92955845`,
VS `0x4aec30af299c282c`. The supplied fade constant produces alpha 1. A diagnostic
draw skip revealed the title background, and was removed. Native/guest debugger attempts
were inconclusive: a guest watchpoint hit a host FEX single-step crash; software breakpoints
were refused as busy, and detach ended a separate guest run. Those are debugger-induced
failures, not evidence of the original black-screen cause. All debugger sessions/forwards
were released and the guest-debug-port / HLE caller-log overrides cleared.

The final inventory still has 12 distinct refused symbols (kernel signal/context,
module teardown and miscellaneous file/query functions). None was observed as the terminal
call in the final run; this does not claim complete compatibility for those families.

### Where the frame goes

Capture 1 has 195 complete SDK frames, mean 76.96 ms. On `GpuComm`, each frame has about
3 `Vulkan.TimelineWait` calls totaling **49.42 ms**, 3,058 `Rasterizer.Draw` calls totaling
**23.92 ms elapsed**, and 5 submissions. `Guest-1` spends **58.94 ms/frame** inside the
submission admission gate. These cross-thread times overlap and must not be added.

The same-run KGSL/scheduler overlap is 4.523 s with no dropped/overwritten trace records;
clock uncertainty is 1.104 us. `GpuComm` is on CPU for 1.359 s, sleeping for 2.870 s and
runnable for 0.294 s. KGSL waits of roughly 45 ms complete successfully and consume only
tens of microseconds of CPU. GPU busy is 67.2%; observed GPU frequency is 615 MHz, with
`thermal_pwrlevel=0` and `throttling=0` at both ends. This is neither a saturated single CPU
core nor evidence of current thermal throttling. Yesterday's 401 MHz screenshots remain
a separate, uncontrolled device-state difference.

Detailed GPU queries in capture 4 show about **40.6–48.0 ms per GPU.GuestFrame** in two
one-second observation windows. There are 3 `GPU.HostReadback` samples per guest frame,
totaling about **0.028 ms/frame**. The copies themselves are cheap; the synchronous wait
also waits for preceding rendering. These are GPU elapsed durations, not calibrated
CPU/GPU timeline attribution. Shader compilation and texture uploads are not the sustained
hotspots in the baseline; `Texture.Stage` totals only 3.31 ms over the 15-second capture.

### Why completion mode helps, and what is still unproven

`TextureCache::FindRenderTarget` / `FindTexture` queue linear or width <= 8 images for
writeback. In parse mode, Liverpool's EOP/EOS path calls `ProcessDownloadImages(true)`;
`DownloadImageMemory` submits and waits through `Scheduler::Finish()` for each image.
This blocks command production and backs up the GNM submission gate. In completion mode,
that path records the copy and defers the CPU writeback until GPU completion, together
with later fence signaling.

In both valid completion captures, `GpuComm` has **no completed TimelineWait scopes**;
its largest elapsed wait becomes `PM4.IdleWait`. Switching back restores approximately
3 timeline waits per frame (3.450 s over the 5.988 s return capture), and switching to
completion again removes them. The screenshots retain the ground/tree/enemy textures
without the previous broad striped corruption. This identifies an actionable overlap/
synchronization problem while retaining the readbacks.

Completion mode also changes fence-label timing; this experiment does not isolate every
part of that change, prove that all three image writebacks are needed, or validate long
gameplay. Precise versus Relaxed and linear on/off were not separately tested. Neither
disabling readbacks nor enabling completion by default is accepted as a final fix. The next
implementation should preserve CPU visibility and fence ordering while reducing per-image
blocking, then repeat at 100% and validate longer gameplay. GPU rendering and thousands of
host draw calls remain significant costs even after that work.

### White screen: textures that sample a corner of a larger target

The auto-exposure chain renders luminance into the top-left corner of a 1920x1080 target
(through the viewport). It then samples it with a smaller texture descriptor at the same

### Frame stalls: synchronous image write-backs

With linear readbacks, every linear image the GPU writes is copied to guest memory at the
next fence, or at the end of the submission. In parse mode the command processor
`Scheduler::Finish()`es the GPU for each one. In the indoor scene below, that meant
2–3 write-backs per frame and **9.7 ms per frame waiting**, about half of the frame. It also
drained the GPU before the next frame's commands were recorded.

Earlier, deferring all write-backs corrupted textures. Two reasons explain this:

- Deferred write-backs run on the scheduler's priority thread once the GPU reaches their
  tick. `Finish()` does not wait for that thread.
- `TryWriteBacking` writes the backing directly, so neither the buffer tracker nor the page
  tracker sees it.

Host paths can therefore read guest memory that still holds the bytes from before the GPU
wrote the image: image uploads and their hashes, buffer uploads of CPU-dirty pages, the
stream path, `Rasterizer::CopyBuffer` and the copy-shader HLE guest mirror. A later
synchronous write-back of the same range could also be overwritten by the late deferred one.
In addition, `SettleWaits` performs labels early without the write-backs queued before them.

Change (`upload_diag async_writeback off|tiny|all`, default `all`):

- Each deferred write-back records its range and tick (`TextureCache::AddPendingWriteback`).
  The priority-thread op completes it in queue order.
- `TextureCache::WaitPendingWritebacks(addr, size, reader)` makes those host paths wait for
  overlapping write-backs: it waits for the tick, then for the op. When nothing is pending
  it costs one atomic load. When something is pending, a lock-free test against the bounds of
  all pending ranges skips most calls.
- Synchronous downloads wait for overlapping deferred ones first.
- `SettleWaits` and the GDS store path wait for all pending write-backs before performing
  labels early.
- At fences the write-backs are deferred and the fence follows them. A fence after a
  synchronous batch is deferred while any write-back is pending.
- At the end of a submission, queued write-backs are deferred too
  (`Liverpool::QueueSubmitWritebacks`). A fence that writes nothing orders flips
  (`FenceMark`) and later fences after them.
- Counters in `upload_diag status`: `async_writeback` (deferred fences and submits),
  `writebacks` (sync/async, and the sync ones at fences and at submits), and
  `writeback waits` per reader with total wait time. The bounded write-back log is re-armed
  with `upload_diag writeback_log <n>`.
- This replaces the earlier tiny-only switch; `tiny` mode keeps that behaviour.

Same session, same standing position indoors (`waits.py`, guest flips over 8 s, 60 FPS cap):

| async_writeback | FPS | sync write-backs/frame | Finish/frame |
| --- | ---: | ---: | ---: |
| off | 49.4 | 2.98 | 2.98 |
| all | 59.9 | 0 | 0 |
| off | 50.3 | 3.00 | 3.00 |
| all | 60.0 | 0 | 0 |

### Ground shadow trail following Kratos (2026-10-17)

Symptom (Odin3, any render scale): a large dark patch on the floor around Kratos that moves with
him; fragments of old shadows stay behind.

Cause, from a guest command trace and an Android GPU replay of the Hades scene:
- Each frame the game renders its cascades into one 2048² D32S8 atlas and projects each cascade
  into a 1920×1080 2×MSAA shadow mask `0x2c42d0000` with MIN blending (`CB_BLEND0_CONTROL
  0x61410141`), cascade pixels chosen by depth bounds and stencil.
- Before that, draw #31 clears the mask with a full-screen rect (viewport and scissor
  1920×1080). The 960×540 half-resolution depth of the previous pass is still bound; the draw
  does not use it (`DB_DEPTH_CONTROL 0x772`: depth test ALWAYS, no write, stencil off).
- We attached that depth, so the Vulkan render area shrank to 960×540 and only the top-left
  quarter of the mask was cleared. Everywhere else MIN kept every earlier frame's shadows: on the
  device they piled up where Kratos walked; in a desktop replay of the same record (mask rebuilt
  from empty memory) the whole floor was black.
- Ruled out on the way: depth bounds on Adreno (forcing the depth test on for bounds-only draws
  changed nothing), depth bias, Z clip/clamp, viewport depth, the linear-depth pass (dumped and
  aligned with the screen), the blob-shadow pass (skipping it changed nothing), predication
  (`SET_PREDICATION` is unimplemented; every predicated draw is drawn).

Fix: `Regs::DepthUnusedAndSmaller` — a depth surface the draw neither tests nor writes (depth
ALWAYS without writes, no stencil or bounds test) that is smaller than a bound color target is
not attached, in both the pipeline key and `PrepareRenderState`, so the render area covers the
whole color target and the mask keeps its 2× samples. Only draws where the depth would shrink
the render area change. `upload_diag unused_small_depth drop|keep` (default drop) switches it
live and counts dropped draws.

after, it is lit with a normal Kratos shadow. Odin3 APK `a8ec380f` (host `c9ecee44`): the floor is
